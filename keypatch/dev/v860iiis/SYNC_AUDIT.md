## 1. 镜像身份、基址与向量表

- 大小 79300 B（0x135C4），sha256 与给定值一致。
- 向量表（文件偏移 0，按 base 0x08003000 解释）：

```
v[ 0]=0x20001548  v[ 1]=0x080030D5  v[ 2]=0x0800E485  v[ 3]=0x0800C039
v[ 4]..v[10]=0        v[11]=0x08010D91  v[12]=v[13]=0
v[14]=0x0800E8A9  v[15]=0x08011AA5
```

- `v[0]` 在 RAM（0x2000_0000..0x2000_2000）且 8 字节对齐；`v[1]` 为 Thumb 地址；
  其余非零向量全部落在 `[0x08003000, 0x080165C4)` 内。
- Reset 处理函数（base+0xD4）与 `__main` 桩（base+0xC0）：

```
0x080030D4  04 48        ldr  r0, [pc, #0x10]   ; [0x080030E8]=0x08011B29 (SystemInit|1)
0x080030D6  80 47        blx  r0
0x080030D8  04 48        ldr  r0, [pc, #0x10]   ; [0x080030EC]=0x080030C1 (__main=base+0xC0|1)
0x080030DA  00 47        bx   r0

0x080030C0  03 48        ldr  r0, [pc, #0xc]    ; [0x080030D0]=0x20001548 == 向量[0] SP
0x080030C2  85 46        mov  sp, r0
0x080030C4  00 f0 7c f9  bl   0x080033C0
0x080030C8  00 48        ldr  r0, [pc, #0]      ; [0x080030CC]=0x08013CE5 (main|1)
0x080030CA  00 47        bx   r0
```

- `__main` 桩位于文件偏移 0xC0，其字面量等于向量[0]（SP）=> **base = 0x080030C0 − 0xC0 = 0x08003000**，
  不依赖假设。镜像末端 = 0x08003000 + 0x135C4 = **0x080165C4**。
- 由 `__main` 桩最后一个 `ldr/bx` 可得 **主循环/主任务入口 = 0x08013CE4**（字面量 0x08013CE5）。

## 2. 内核判定：Cortex-M0 / ARMv6-M（Thumb-1）

### 2.1 方法 A：干净函数体（最可信口径）

函数入口集合 = 向量表 6 项 + veneer 3 项（`0x080030C8→0x08013CE4`、
`0x080030D4→0x08011B28`、`0x080030D8→0x080030C0`）+ 全镜像 BL 目标，去重 **447 个入口**。
从每个入口线性解码到首个返回/无条件分支（跳过数据/字面量池）：

- 共 **11,428 条**指令；
- 4 字节指令 **857 条，全部是 BL（100.0%）**；
- **4 字节非 BL 指令 = 0**。

若目标是 Cortex-M3/M4（Thumb-2），编译器必然在函数体中大量生成 `movw/movt/ldrd/strd/
ubfx/bfi/ldr.w/str.w/…`；实测为 0。

### 2.2 方法 B：全镜像线性反汇编（skipdata）与"数据误判"可信度

- 全镜像共解出 **37,250 条**指令（`skipdata` 兜底 212 条）；
- 4 字节 **2,400 条**，其中 BL **2,172 条**（90.5%），非 BL **227 条**；
- 关键可信度指标：**227 条 32 位非 BL 解码中，落在任何真实函数体内的 = 0 条**
  => 全部是数据/常量池被误判（不对应任何可执行代码）。
- 这 227 条里 193 条是协处理器/NEON 编码（`cdp2` 81、`mrc2` 40、`ldc2l` 16、
  `mcr2` 9、`v…` 等，Cortex-M 根本不存在这些协处理器）；其余 34 条（`and` 10、
  `strb.w` 9、`strb` 4、`ldrb.w` 3、`ldrd` 1、`addw` 1、`b.w` 1 等）也全部位于
  字面量池/常量表内（函数体外）。
- **M4 特征指令**（`movw/movt/ldrd/strd/ubfx/sbfx/bfi/bfc/clz/sdiv/udiv/mla/mls/rbit`）
  全镜像只命中 **1 条**：`0x080161E8 ldrd r0,r4,[r3,#0x3d8]`，位于 0x08016000 起的
  图形/查表数据区（真实函数体外）；真实函数体内 = 0。

### 2.3 方法 C：无硬件除法（M0/M3 特征，M4 不符）

- `__aeabi_uidiv` @ **0x080030F0**：22 条自包含指令（`push {r4,r5,lr}` … `pop {r4,r5,pc}`），
  **函数体内无 BL**，含 `bgt 0x080030FE` 回边循环，逐位长除法（r0=商、r1=余）。
- 同步字函数在 0x080115C0 调用它。
- Cortex-M4 有硬件 `UDIV/SDIV` 指令，编译器不会生成 `__aeabi_uidiv`；真实函数体中
  也没有任何 `udiv/sdiv` 指令。

### 2.4 结论与 Unicorn 模式

**内核 = Cortex-M0 / Thumb-1（ARMv6-M）。**

- 可信度：数据误判规模仅 227/37,250 = **0.6%**，且 100% 在函数体外；真实函数体
  11,428 条指令 0 条 32 位非 BL、0 条 Thumb-2 特征指令 => 结论可信度高。
- Unicorn 应使用 `Uc(UC_ARCH_ARM, UC_MODE_MCLASS)`（与 V1C 审计一致；Unicorn 没有
  独立 M0 模式，MCLASS 覆盖 Cortex-M；**不适用** M4/Thumb-2 假设）。
  实测：镜像中只有 Thumb-1 + 32 位 BL，MCLASS 可正确执行（见 §9）。

## 3. 同步字函数 0x080115B8..0x080115EF（56 B）

### 3.1 原始 56 字节（逐字节与 Lead 给定值一致）

```
+0x00: 0c 4a 10 b5 41 1c 10 46 f1 f7 96 fd 04 46 01 0a
+0x10: 04 20 02 f0 ac f9 e1 b2 05 20 02 f0 a8 f9 14 20
+0x20: 02 f0 5e f8 33 20 02 f0 03 fa 7d 20 c0 00 02 f0
+0x30: 57 f8 10 bd 68 c3 00 00
```

即：
`0c4a10b5411c1046f1f796fd0446010a042002f0acf9e1b2052002f0a8f9142002f05ef8332002f003fa7d20c00002f057f810bd68c30000`
（+0x34 处 4 字节字面量 = `68 c3 00 00` = 50024）。

### 3.2 逐条语义（20 条指令，代码 52 B + 字面量 4 B）

| 地址 | 字节 | 指令 | 语义 |
|---|---|---|---|
| 0x080115B8 | 0c 4a | `ldr r2,[pc,#0x30]` | r2 = 字面量 @ **0x080115EC(=+0x34)** = 50024 |
| 0x080115BA | 10 b5 | `push {r4, lr}` | 保存现场 |
| 0x080115BC | 41 1c | `adds r1, r0, #1` | r1 = ID + 1（r0 为传入 ID） |
| 0x080115BE | 10 46 | `mov r0, r2` | r0 = 50024 |
| 0x080115C0 | f1 f7 96 fd | `bl 0x080030F0` | `__aeabi_uidiv(50024, ID+1)` → r0 = **sync = 50024//(ID+1)** |
| 0x080115C4 | 04 46 | `mov r4, r0` | r4 = sync |
| 0x080115C6 | 01 0a | `lsrs r1, r0, #8` | r1 = SYNC1 = sync>>8 |
| 0x080115C8 | 04 20 | `movs r0, #4` | reg = 4（SYNC1） |
| 0x080115CA | 02 f0 ac f9 | `bl 0x08013926` | **WriteReg(4, sync>>8)** |
| 0x080115CE | e1 b2 | `uxtb r1, r4` | r1 = SYNC0 = sync & 0xFF |

| 0x080115DC | 33 20 | `movs r0, #0x33` | 0x33 = SCAL |
| 0x080115DE | 02 f0 03 fa | `bl 0x080139E8` | **strobe(0x33)**（CC2500 频率合成器校准） |
| 0x080115E2 | 7d 20 | `movs r0, #0x7d` | 125 |

| 0x080115EC | 68 c3 00 00 | 数据 | **50024 (0xC368) 字面量（+0x34）** |

### 3.3 50024 唯一性与边界

- 四字节模式 `68 c3 00 00` 全镜像**只出现 1 次**：`0x080115EC`（文件偏移 0x0E5EC）。
- 引用它的 `ldr(literal)` 指令**只有 0x080115B8** 一条。
- **函数边界（独立证据）**：
  - 顺序解码 20 条指令，代码止于 0x080115EA，+0x34 字面量占 0x080115EC..0x080115EF，
    因此函数精确占 **0x080115B8..0x080115EF（56 B）**；
  - **下一函数起点 = 0x080115F0**：该地址是真实函数入口，被 `0x0800CD80` 的
    `bl 0x080115F0` 调用；从 0x080115F0 起线性解码为合法函数体
    （`ldr r0,[pc,#0x28]; ldrh r2,[r0,#0xc] …`），止于 0x08011618 `bx lr`；
    其字面量池在 0x0801161C..0x0801162B（0x2000045E / 0x200004D4 / 0x200004C3 / 0x200004E0），
    再下一个函数入口 0x0801162C（BL @0x08005B18 / 0x0800C664）。
  - **0x080115F4 不是函数入口**：全镜像没有 BL/分支/向量/字面量指向 0x080115F4。
    （Lead 初勘"下一函数 0x080115F4"为笔误，已在本报告更正为 0x080115F0。）
  - 对 `[0x080115B8,0x080115F0)` 的引用检查：只有入口 0x080115B8 被 5 个 BL 指向；
    范围内无任何内部分支/调用目标，也没有字面量池指针指向该范围
    => 56 字节整段原位改写安全。

## 5. 同步字函数的 5 个调用点与 settings[6] 入参

全镜像 `bl 0x080115B8` 的调用点**恰为 5 个**，与 Lead 初勘一致：

| 调用点 | 所在函数区间 | 取 ID 指令 | settings 基址装载 | 触发路径 |
|---|---|---|---|---|
| 0x08005A78 | 0x080059E4..0x08005A7C | 0x08005A76 `ldrb r0,[r0,#6]` | 0x08005A26 `ldr r0,=0x20001058` | 主循环 0x08013CE4 → 状态轮询 0x080058E4（0x08013DAE 调用）→ 改值处理 0x080059E4（0x0800592E 调用）→ **cmp r1,#6（C.Fn 项==6/ID）** → sync |
| 0x08005E36 | 0x08005DD0..0x08005E52（RF 初始化） | 0x08005E34 `ldrb r0,[r0,#6]` | 0x08005E32 `ldr r0,=0x20001058` | 整机初始化 0x08012364（0x080123C8 调用）/ 0x08011C08 处调用 → **RF 初始化 0x08005DD0** → sync（无条件） |
| 0x0800C5C2 | 0x0800C528..0x0800C5C6 | 0x0800C5C0 `ldrb r0,[r0,#6]` | 0x0800C56A `ldr r0,=0x20001058` | 主循环 → 状态轮询 0x080058E4（0x08005928 调用）→ 改值处理 0x0800C528 → **cmp r1,#6** → sync |
| 0x0800D0BA | 0x0800CD7C..0x0800D124（事件分派） | 0x0800D0B8 `ldrb r0,[r4,#6]` | 0x0800D094 `ldr r4,=0x20001058` | 主循环 0x08013CE4 → 事件分派 0x0800CD7C（0x08013DAA 调用）；`r2==4` 分支：把 settings 区恢复默认值 → `bl 0x080128F0` → sync（**设置恢复/默认化路径**） |
| 0x0800D0E6 | 0x0800CD7C..0x0800D124（事件分派） | 0x0800D0E4 `ldrb r0,[r0,#6]` | 0x0800D0E2 `ldr r0,=0x20001058` | 主循环 → 事件分派 0x0800CD7C；`r2==0x300` 分支：`bl 0x08005E54`（RF 重初始化）→ `bl 0x080128F0` → sync（**重新初始化路径**） |

静态数据流证明（CFG 路径集合，非简单线性回溯）：

- 对每个调用点，构造函数区间内指令级 CFG，取"从 settings 基址装载可达 ∧ 能到达 ID 装载"
  的路径指令集合；在该集合上 **基址寄存器无改写**（受检寄存器分别为 r0/r0/r0/r4/r0）。
  例：调用点 0x08005A78 的路径集合 32 条指令、r0 改写 0 处；0x0800C5C2 为 33 条、0 处。
- 5 个调用点在执行 `bl sync` 前 r0 都等于 `*(uint8_t *)(0x20001058 + 6)` =
  `*(uint8_t *)0x2000105E` = **settings[6]（远程 ID）**。

settings 基址旁证：

- 值 `0x20001058` 在镜像字面量池中出现 **30 处**（与 Lead 初勘的"30 处字面量"一致），
  对应的 `ldr(literal)` 装载指令共 **42 条**（同一字面量被多个函数/路径复用）。
- 改值门条件（`cmp rX,#6`）只出现在两个"改值处理"路径（0x08005A72 / 0x0800C5BC）；
  RF 初始化与设置恢复/重初始化路径无条件重设同步字。

## 6. 运行期写 CC2500 寄存器 4/5 的全部路径

全镜像 `bl 0x08013926`（WriteReg）调用点共 **60 个**，逐个静态解析 r0（寄存器号，
含 `movs r0,#imm` 与 `mov r0,rX` 链）——60 个全部可解析。其中写 **reg4/reg5** 的
**恰为 4 个**：

| 调用点 | r0 | 值 | 说明 |
|---|---|---|---|
| 0x080115CA | 4 | `sync>>8` | 同步字函数 SYNC1 |
| 0x080115D2 | 5 | `uxtb(sync)` | 同步字函数 SYNC0 |
| 0x080136F6 | 4 | **0xC3** | CC2500 初始化表 SYNC1 缺省值 |
| 0x080136FE | 5 | **0x68** | CC2500 初始化表 SYNC0 缺省值 |

其余 56 个调用点的寄存器号均不等于 4/5（包括 reg 0x00..0x2E 初始化表其余项、
reg 6 / 0x18 / 0x3E 等运行期配置）。

初始化表与覆盖顺序：

- 初始化表函数入口 **0x080136C8**（`push {r3,r4,r5,lr}`），共 **47 次 WriteReg**，
  寄存器号恰为 **0x00..0x2E 各一次**；
- 该函数只被 RF 初始化函数 **0x08005DD0** 在 **0x08005DE6** 调用一次；
- RF 初始化函数 0x08005DD0 内部顺序：0x08005DE6 先写初始化表（含 reg4=0xC3/reg5=0x68）
  → 读 reg0xD/0xE、`strobe(0x36)`、`WriteReg(0x3E, val)`、`strobe(0x33)`、`delay(1000)`
  → **0x08005E36 调用同步字函数，用 settings[6] 覆盖 SYNC1/SYNC0**。
- 由于 0x08005E36 没有其他分支可达，每次 RF 初始化都必然先写缺省值、后被同步字函数覆盖。

旁路检查（确认没有第三种运行期写法）：

- 底层写 API `0x08013A00` 的直接调用点只有 3 个：`0x08013850`（r0=0x7E 复位/校准序列）、
  `0x08013920`（r0=0x7F 命令）、`0x0801392C`（WriteReg 内部，r0 来自 WriteReg 参数）。
  没有任何直接调用以 r0=4/5 写；
- 读路径 `0x080139BC` 的调用点入参为 `0xff` / `0x80|reg` / `0xc0|reg`，与写 reg4/5 无关。

**结论：运行期只有【同步字函数 0x080115B8】与【CC2500 初始化表 0x080136C8】写
SYNC1/SYNC0；未发现第三处运行期写入。** 因此按 V1C 相同思路把 56B 同步字函数原位
改写即可，无需改初始化表。

## 7. 注入代码洞：无静态可证安全区（本补丁不需要注入）

扫描规则：全镜像 ≥16 字节连续 `0x00`（或 `0xFF`）；对每个区间做**保守**引用检查——
所有 16/32 位编码的 BL、B、Bcc、CBZ/CBNZ 目标；`ldr(literal)` 指令读取目标；
以任意地址（含 Thumb 位）出现的 32 位指针值；向量表；以及真实函数体区间重叠。

- 全镜像 ≥16B 全 0 区间 **27 个**；`0xFF` 区间 **0 个**（镜像内没有任何擦除态空闲区）。
- 27 个全 0 区中，除向量表保留槽位外，其余全部位于 **0x08014000..0x080165C4 的
  UI/图形/查表数据区**（0x08014800~ 的图形/字形区、0x08015000~ 的图标区、
  0x08016000~ 的亮度/曲线 LUT 等），且大多落在被引用数据块内部。

Lead 初勘候选逐一验证：

| 候选 | 实际连续 0x00 | 引用检查 | 结论 |
|---|---|---|---|
| **0x08014060** | **仅 8 B**（<16B） | 存在指针值 0x08014060（数据表指针目标）；位于字面量池之后的数据表起始处 | **不安全/不满足条件** |
| **0x08014B6E** | 26 B | 无分支/无 ldr 目标/无指针/无函数体重叠 | 位于被引用数据块 **[0x08014915,0x08014BCA)** 内部（图形/字形表），无法证明不被表索引读取 => **不安全** |
| **0x080162B9** | 112 B | 无分支/无函数体重叠；3 个 `ldr` 命中全部在数据区（非真实代码）；**1 个真实指针 0x08016328 指向区间最后 1 字节**（该字节是紧邻的下一个被引用表的首字节；指针存于 0x08003890、由真实代码 0x08003734 装载） | 数据表尾部零区；整段改写会破坏被引用表 => **有条件可用/默认不用**；扣除末字节后最多 110 B（入口须偶数 0x080162BA），仍属数据表内部 |

另外，**向量表保留槽位 0x08003010..0x0800302B（槽 4..10，28 B）**：
零引用、位于向量表，对应 ARMv6-M 的 Reserved 异常（硬件永不取用），是镜像内唯一
"确定不会被运行期读取"的零区；但只有 28 B，且修改的是向量表，不建议作为正式注入区。

> **结论：代码洞——无静态可证安全区，本补丁不需要注入。**
> 本镜像没有 V1C `0x08017944`、同平台 V860III-C `0x080179C2`（234 B）那样的"零引用大死区"：
> V860IIIS V1.1 镜像只有 79,300 B（末端 0x080165C4），比 V860III-C（87,612 B）短，
> 其尾部数据表一直排到镜像末端，没有留下整块零区。

对并行任务（C.Fn 菜单/hook）的提示：

- 0x08014000..0x080165C4 是 **UI/图形/LUT 数据区**（含被代码指针引用的数据表），
  其中所有 ≥16B 零区都在数据表内部；**不要在 V860IIIS 上照搬 V860III-C 的
  0x080179C2 注入区**（本镜像不存在该地址空间/该死区）。
- 若后续 C.Fn 方案需要注入 hook，需另行评估（例如扩大镜像尾部，但本审计未验证
  flash 容量与升级器是否接受更长的镜像；不能仅凭静态假设）或改用 56B 原位改写。

## 9. Unicorn 调用级 harness（独立内嵌，不 import 设备模块）

### 9.1 内存布局 / 哨兵 / 桩

| 项 | 值 |
|---|---|
| flash | `0x08003000..0x08017000`（0x14000，镜像 79,300 B 写入 0x08003000） |

| 初始 SP | `0x20001548`（原厂向量[0] 初值） |
| LR 哨兵 | `0x20001FF1`（= 返回落点 `0x20001FF0`，该处写 `b .`；`emu_start(..., until=0x20001FF0)` 停在这里） |
| R4 哨兵 | `0xDEADBEEF`（用于验证 `pop {r4,pc}` 恢复） |
| 桩 | `uidiv(0x080030F0)`：code hook 记录入参 (r0,r1)，用宿主整数除法回填 r0 并令 PC=LR（stub）；`WriteReg(0x08013926)` / `strobe(0x080139E8)` / `delay(0x08013698)`：函数入口改 `70 47`（`bx lr`），code hook 记录参数 |

### 9.2 原厂行为自证（全部 PASS）

| ID | sync = 50024//(ID+1) | 实际调用序列 |
|---|---|---|
| 0 | 0xC368 | WriteReg(4,0xC3) → WriteReg(5,0x68) → delay(20) → strobe(0x33) → delay(1000) |
| 1 | 0x61B4 | WriteReg(4,0x61) → WriteReg(5,0xB4) → delay(20) → strobe(0x33) → delay(1000) |
| 5 | 0x2091 | WriteReg(4,0x20) → WriteReg(5,0x91) → delay(20) → strobe(0x33) → delay(1000) |
| 37 | 0x0524 | WriteReg(4,0x05) → WriteReg(5,0x24) → delay(20) → strobe(0x33) → delay(1000) |
| 99 | 0x01F4 | WriteReg(4,0x01) → WriteReg(5,0xF4) → delay(20) → strobe(0x33) → delay(1000) |

## 10. 风险与未决问题

1. **无实机验证（最高风险）**：本轮只有静态复核 + Unicorn 单函数调用级验证；没有整机
   模拟、没有真实 V860III-S + CC2500 的 RF bring-up，也没有任何真机刷写。若后续按
   V1C 思路做同步字补丁，必须在真机上验证上电首包、ID 切换/掉电保持、与原厂引闪器互操作。
2. **无静态可证安全的注入区**：本镜像没有 V1C/V860III-C 式大死区。若后续补丁方案需要
   注入 hook（如 C.Fn 开关 + 改值 hook），不能假设 `0x080179C2`/`0x08017944` 可用；
   候选区均有数据/指针风险（§7）。本同步字审计本身不需要注入。
3. **镜像外 flash 未知**：镜像只到 0x080165C4；其后的 flash 内容/容量与升级器是否接受
   更长的镜像均未验证（同平台设备常见 128KB flash，但不能据此推断本设备/升级器行为）。
   任何"在镜像尾部追加代码"的方案必须由硬件/升级器验证后再采用。
4. **事件分派函数 0x0800CD7C 内部有间接/复杂分支**：本审计对调用点 4/5 的所属函数用
   "最大已知入口 ≤ 调用点 + 函数区间 [0x0800CD7C,0x0800D170)" 定位，并核对了
   settings 数据流；但该函数内部含函数指针/事件码分派，触发路径的"事件码 4 / 0x300"
   语义仍是静态推断（未实机确认对应哪个用户操作）。
5. **间接/复杂控制流结构**：0x0800CD7C（事件分派）内部通过 `0x0800CF9C` 调用
   0x0800C9EC（状态/命令处理），并直接调用 0x0800CACC / 0x0800CBBC / 0x0800CCB0 等
   子函数；说明固件存在多层间接控制流。本审计的 CFG 统计只覆盖可静态到达的 447 个
   函数入口，未达部分按"数据"处理（§2 可信度已计入）。
6. **固件版本锁定**：本报告只对 `V860IIIS_V1.1.bin`（sha256 `bdc8f354…0b20`）有效；
   任何其它版本必须重新审计地址/字节/调用点。
7. **C.Fn 数据区（供 task-1/task-2 参考）**：0x08014000..0x080165C4 为 UI/图形/LUT 数据区，
   零区全部在数据表内部；同平台 V860III-C 的 C.Fn 最大/回绕表位于其 0x080181AA，
   但 **V860IIIS V1.1 的镜像更短（末端 0x080165C4），不能假定同地址可用**。
8. **ID=0 语义**：原厂 ID=0 时 `sync = 50024//1 = 0xC368`，恰好等于 CC2500 初始化缺省值
   （0xC3/0x68）。若后续采用"ID=0 → KEY"的补丁语义，需在文档中明确该变化；且补丁后
   ID=0 若被 C.Fn 菜单使用，需确认菜单允许 0 值（本审计未做 UI 验证）。
