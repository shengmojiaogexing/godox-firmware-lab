## v3-1. 语义（与 task-4 相同，未变）

- **KEY_ON=1（密钥模式）**：每帧 `SYNC=KEY(0xD798)` → 发第一帧 → `SYNC=floor(50024/(当前ID+1))` → 发第二帧 → 恢复 `SYNC=KEY`。
  第二帧同步字**随当前 ID 动态计算**（ID=0→0xC368、1→0x61B4、37→0x0524、99→0x01F4，不是固定 0x01F4）。
- **KEY_ON=0（普通模式，出厂默认）**：先写原厂同步字（`floor(50024/(当前ID+1))`）再单发；ID 0..99 原厂含义不变。
- **开关**：长按 PA6 → 注入计数到 34（≈1.5s）翻转 KEY_ON 并置 latch；松开计数/latch 清零；按住期间只触发一次。
  MAIN 主循环 `0x0802B282 bl 0x08027E44` 每轮调用；注入代码执行完后重建原厂 `push.w {r3..r11,lr}` 并跳回 `0x08027E48`。
- **原厂 PA6 长按动作禁用（两处）**：`0x0802830A` 与 `0x080284F2` 的 `cmp r3,#0x21` 均改成 `cmp r3,#0xFF`；
  两个动作块 `0x08028310` / `0x080284FA` 在成品中均不可达（详见 v3-§9）。
- KEY_ON 为 **RAM 版**：重启/换电池后回普通模式。

## v3-7. 与 Lead 口径的差异 / 已解决疑点

1. **数字口径**：task-7 写“差异 370 B、补丁点 6 区域/7 改动位置”与实测**一致**；
   其中 0x0802830A / 0x080284F2 都是 2 字节 `cmp` 指令但**各只改 1 个字节**（`21 2b`→`ff 2b`）。
2. **task-4 疑点 2 已解决**：`0x080284F2` 已改 `#0xFF`。独立确认其动作块 `0x080284FA`
   **无任何分支目标**，且 fall-through 被恒成立的 `bls.w 0x0802814A` 跳过 → 该动作块**不可达**。
   动作块 1（`0x08028310`，下游关机 `0x0802B7D0`）同样不可达。
3. **残余说明**：状态机中 `[0x20000087]==0x14 且 [0x20001089]!=0` 分支的 PA6 长按原厂动作
   （置 countdown 状态 0x16）现在也一并被禁用（符合“长按只用于密钥开关”的设计）；
   该状态分支的其它行为保留。实机验证时留意该状态下长按 PA6 不再有原厂动作属于预期。
4. **持续按住计数器**：补丁后按住 PA6 超过 34 次扫描时原厂计数器 `0x20000F92` 继续增长
   （松开路径 `0x08027FFC` 清零）；因两处动作块均已不可达，不会再触发原厂动作（残余影响极小）。

## v3-8. 风险与未验证项（最终版）

1. **键位需实机确认**：静态只能确定 PA6 是“原厂长按会进关机流程”的键；若实机手感/位置不合适，
   改 `BTN_MASK` 为 `0x10`(PB4) 或 `0x20`(PB5) 重新生成即可。
2. **RAM 版开关**：KEY_ON 不持久化，关机/换电池后回普通模式，需重新长按。
3. **原厂 PA6 长按动作被占用**：两处原厂长按动作均禁用；关机需用电源键长按/菜单（电源键路径静态独立，未实机验证）。
4. **双发时序**：KEY_ON=1 时每帧 2 次发射（TX4 +≈600µs、TX2 +≈500µs；D5 短命令原厂连发 3 次时成倍放大）；
   按键响应/HSS/连拍是否受影响未量化。异常时可关 `DUAL_SEND`（只发 KEY 帧）。
5. **未关中断**：注入区无 `cpsid/cpsie`；恢复 KEY 的那次写不在射频忙区间，理论有几十 µs 竞态窗口。
6. **无整机模拟器 / 无实机刷机**：仅调用级证据（capstone + Unicorn 单函数）；无 boot/中断/NVIC/UI 验证；
   bootloader 是否校验 app 未确认。刷机风险自担，建议安全阶梯。
7. **静态扫描局限**：无法排除 DMA / 运行时间接指针引用注入区；`0x081C0000..0x081C0800` 静态零引用。
8. **只验证了 KEY=0xD798**（换 key 可 `--key` 重跑）。

## 1. 目标语义（被验证对象）

- **密钥模式 = ID 菜单值 99**：
  1) 发送帧前把 CC2500 同步字写为私有 KEY `0xD798`（SYNC1=0xD7 / SYNC0=0x98），发第一帧；
  2) 再把同步字写为 `floor(50024/(99+1)) = 500 = 0x01F4`（即原厂 ID=99 的同步字），发第二帧（兼容未打补丁的原厂灯，需其 ID=99、同频道）；
  3) 最后把同步字恢复为 KEY，保证后续异步/中断路径发出的帧仍用密钥同步字。
- **普通模式 = ID 0..98**：完全保持原厂行为（单发，同步字 = `floor(50024/(ID+1))`）。
- 同步字写入时机（新版关键点）：每个蹦床先执行原厂 `bl 0x0802EC64`（射频唤醒/置忙），**之后**才写 CC2500 reg4/reg5，再跳回原函数体发帧。

## 2. 镜像基址 `0x08020000` 的推导证据

| (h) **决定性证据**：Reset_Handler 先调用 `0x08030BBC`（SystemInit 类），其中 | `ldr r0,[pc]→0xE000ED00`（SCB），`ldr r4,[pc]→0x08020000`，`str r4,[r0,#8]` ⇒ **SCB->VTOR = 0x08020000** |

## 3. 同步字函数 `0x0802F040`：边界、原厂公式、写入序列

### 3.1 函数边界

- 入口 `0x0802F040`，原厂字节（前 0x5C）：

```
0x0802F040: 01 22 03 46 10 b5 | 4c f2 68 34 | 13 44 | b4 fb f3 f4 | 82 b0 ...
            movs r2,#1; mov r3,r0; push {r4,lr}; movw r4,#0xC368; add r3,r2; udiv r4,r4,r3
```

- 函数最后一条指令：`0x0802F096: b.w 0x0802B5DC`（尾调用 delay_us(700)）。
- 最后指令结束于 `0x0802F09A`（`0x0802F040 + 0x5A`），`0x0802F09A: 00 bf` 为 2 字节对齐 NOP；
- 下一函数入口 `0x0802F09C: push {r4,lr}`（该函数另有 2 个静态调用点 `0x0802F6B8` / `0x0802F90C`）。
  → 即“函数体长 0x5A、下一函数 0x0802F09C”成立，但 0x0802F09A..0x0802F09B 是 NOP 对齐（见 §15-3）。

### 3.2 原厂公式（`0x0802F046` 起 10 字节）

```
0x0802F046: 4c f2 68 34   movw r4, #0xC368       ; 50024
0x0802F04A: 13 44         add  r3, r2            ; r2 已由 0x0802F040 置 1 -> r3 = ID + 1
0x0802F04C: b4 fb f3 f4   udiv r4, r4, r3        ; r4 = floor(50024/(ID+1))，无符号除法
```

Unicorn 对原厂镜像实测（`reg4/reg5` 单字节写 + 20us/SCAL/1ms/SIDLE/700us 序列全部复现）：

|---|---|---|---|---|---|---|---|---|
| SYNC | 0xC368 | 0x61B4 | 0x4122 | 0x0524 | 0x03D4 | 0x02A4 | 0x01F9 | **0x01F4** |

### 3.3 写寄存器与时序序列

| 地址 | 指令 | 说明 |
|---|---|---|
| `0x0802F058` | `movs r0,#4` → `0x0802F05E bl 0x0802E71C` | 写 CC2500 reg4 = SYNC1 |

## 4. 设置结构 `0x20001768` 与 ID=99 可达性

| 证据 | 内容 |
|---|---|
| 设置结构字面量 | `@0x0802F268 = 0x20001768`、`@0x0802F938 = 0x20001768`、`@0x080299B8 = 0x20001768` |
| 通道/ID 布局 | 调用点先 `ldrb r0,[r4]`（通道）再 `ldrb r0,[r4,#1]`（ID）→ `[+0]=channel`、`[+1]=ID` |
| ID 菜单钳位片段 | 起始 `0x08029996`，原厂字节 `07 4b 07 4a 19 78 53 78 31 b1 0a 33 db b2 63 2b 88 bf 63 23 53 70 10 bd 01 33 db b2 f7 e7` |
| 钳位逻辑 | `ldrb r1,[0x20000F9C]`（+10 标志）→ `ldrb r3,[0x20001768+1]` → 标志=0 走 `adds r3,#1`（`0x080299AE`），标志≠0 走 `adds r3,#0xa`（`0x080299A0`）→ `cmp r3,#0x63`（**实际地址 0x080299A4**）→ `it hi; movhi r3,#0x63` → `strb r3,[r2,#1]`（写回设置）|
| Unicorn 片段执行（栈上准备 pop 返回） | (ID=98,+1)→99；(99,+1)→99 钳位；(89,+10)→99；(98,+10)→99 钳位；(0,+1)→1；(0,+10)→10 |

结论：ID=99 **可由菜单 +1 / +10 步进到达且为上限**；且该字节正是同步字函数与 TX 包装读取的 ID。

## 5. 全镜像写 CC2500 reg4/reg5 的唯一性

方法：扫描全镜像所有 `bl 0x0802E71C`（write_reg）调用点，并用“能连续解码到调用点”的最长回看窗口做 r0 常量传播；另检查 `0x0802ECB4`（单字节写 thunk，r0 由调用者传入）的调用点。

| 项 | 结果 |
|---|---|
| write_reg 直接调用点 | **80 个**（r0 常量回溯 **79 个**；另 1 个在单字节写 thunk 内部，r0 由调用者传入，见下） |
| 写 **reg4 / reg5** 的调用点 | **恰 4 处**：`0x0802E950`、`0x0802E962`（初始化表）、`0x0802F05E`、`0x0802F06E`（同步字函数） |
| 初始化表写入值 | reg4 ← `0xC3`、reg5 ← `0x68`（原厂 SYNC 复位值，字节见 `0x0802E942: c3 22 … 04 20`、`0x0802E954: 68 22 … 05 20`） |
| burst 写 `reg 0x44`（= reg4/5 连写） | 原厂镜像 **0 处**；成品只在注入区 `0x081C0074`（set_sync）新增 1 处 |
| 字节写 thunk `0x0802ECB4` 的调用点 | 2 处：`0x0802543C`（r0=0x18）、`0x08025450`（r0=6），均非 4/5 |
| 回看窗口外的 3 个高寄存器传参点 | 人工反汇编确认：`0x0802E974` r0=fp=6、`0x0802EA5A` r0=sl=0x13、`0x0802EAE4` r0=sb=0x1B、`0x0802EB06` r0=r6=0x1D、`0x0802FA32` r0=sb=0 —— 均非 4/5 |

结论：**原厂镜像写 CC2500 reg4/reg5 仅 4 处**（初始化表 2 处随后被同步字函数覆盖；同步字函数 2 处为实际生效路径），
补丁未引入第 5 条意外路径。

## 8. 注入区 `0x081C0000` 布局与反汇编核对

独立脚本用“期望指令表”（74 条指令 / 232 字节）逐条比对 capstone 线性反汇编，**完全一致**。

| 标签 | 地址 | 大小 | 作用 |

| `inj_sync` | `0x081C0000` | 26 B | 同步字函数分流：`cmp r0,#99`；=99 → `movw r4,#KEY`；否则执行原厂 `movw r4,#0xC368; add r3,r2; udiv`；两者都 `b.w 0x0802F050` 回原厂流程 |

| `inj_tx2` | `0x081C003E` | 36 B | TX2 包装，同上（蹦床换成 `tramp2_*`） |
| `set_sync` | `0x081C0062` | 26 B | `set_sync(r0=16 位同步字)`：栈上 2 字节缓冲 → `write_reg(0x44, buf, 2)`（burst 写 reg4/5） |
| `set_key` | `0x081C007C` | 8 B | `movw r0,#0xD798; b.w set_sync` |
| `set_ord` | `0x081C0084` | 8 B | `movw r0,#0x01F4; b.w set_sync` |
| `tramp4_key` | `0x081C008C` | 18 B | `push {r4,lr}; bl 0x0802EC64; movw r0,#KEY; bl set_sync; b.w 0x0802EDCA` |
| `tramp4_ord` | `0x081C009E` | 18 B | `push {r4,lr}; bl 0x0802EC64; movw r0,#0x01F4; bl set_sync; b.w 0x0802EDCA` |
| `tramp4_orig` | `0x081C00B0` | 10 B | `push {r4,lr}; bl 0x0802EC64; b.w 0x0802EDCA` |
| `tramp2_key` | `0x081C00BA` | 18 B | 同 tramp4_key，恢复点 `0x0802EE32` |
| `tramp2_ord` | `0x081C00CC` | 18 B | 同 tramp4_ord，恢复点 `0x0802EE32` |
| `tramp2_orig` | `0x081C00DE` | 10 B | 同 tramp4_orig，恢复点 `0x0802EE32` |

关键核对结果（全部 PASS）：

- 入口 `B.W` 目标：`0x0802EDC4→0x081C001A`、`0x0802EE2C→0x081C003E`、`0x0802F046→0x081C0000`；字节与独立实现的 B.W 编码一致。
- 常量：KEY `0xD798`（`inj_sync` 1 次 `movw r4`、`set_key`+2 个 key 蹦床共 3 次 `movw r0`）；`0x01F4` 出现 3 次（`set_ord` + 2 个 ord 蹦床）。
- ID 分支：`cmp r0,#0x63` 1 处（`inj_sync`）+ `cmp r3,#0x63` 2 处（两个 TX 包装）。
- **蹦床顺序**（6/6）：`push {r4,lr}` → `bl 0x0802EC64`（唤醒/置忙）→ 写同步字 → `b.w` 原函数体。
  即“同步字写在 0x0802EC64 之后”，静态顺序 + Unicorn 事件顺序（wake 先于 sync）双重复核。
- 栈平衡（静态）：9 个 `push {r4,lr}` / 5 个 `pop {r4,pc}`；其余 3 个 push 由原函数体末尾的 `pop {r4,pc}` 配对
  （TX4 `0x0802EE1E`、TX2 `0x0802EE8C` 已核对）。Unicorn 每次运行结束 `SP == 0x20007000` 初值，动态亦平衡。
- 注入区直接内存写仅 2 处（栈缓冲 `strb r3,[r1]` / `strb r4,[r1,#1]`），其余通过 `write_reg`。
- 注入区**无** `cpsid/cpsie`（关中断缺失，见 §14 风险）。

| 成品注入区外部跳入 | **恰 3 处**：`0x0802EDC4→0x081C001A`、`0x0802EE2C→0x081C003E`、`0x0802F046→0x081C0000` |
| 成品注入窗口字面量引用 | 0 处（补丁只加分支立即数，不加数据指针） |

> 在原厂镜像中有配置/参数表引用（静态扫描可见），但本补丁窗口 `0x081C0000..0x081C0400` 无任何引用。

## 10. Unicorn 调用级验证（桩替换）

Harness：独立映射 FLASH `0x08000000+2MB` / RAM `0x20000000+32KB`；桩替换
`write_reg(0x0802E71C)`、`strobe(0x0802E88C)`、`delay_us(0x0802B5DC)`、`radio_wake(0x0802EC64)`、
GPIO 写/读（`0x08032A64`/`0x08032A58`）；在 `0x20006000` 放 `b .` 哨兵作为返回地址，记录事件序列。

### 10.1 同步字函数

| 镜像 | ID | 实测 SYNC | 期望 |
|---|---|---|---|
| 原厂 | 0/1/2/37/50/73/98/99 | 0xC368/0x61B4/0x4122/0x0524/0x03D4/0x02A4/0x01F9/0x01F4 | 50024/(ID+1) ✔ |
| 补丁版 | 0/1/2/37/50/73/98 | 与原厂逐位相同 | ✔ |
| 补丁版 | 99 | **0xD798（KEY）** | 密钥模式 ✔ |

原厂/补丁版普通模式的后续序列均为 `reg4 单写 → reg5 单写 → delay20 → strobe0x33 → delay1000 → strobe0x36 → delay700`，SP 平衡。

### 10.2 发送入口（事件序列 = wake / SYNC / FIFO / STX / 延时 / SFTX / SIDLE）

| 场景 | 实测序列 |
|---|---|
| 原厂 TX4(ID=0) | `wake → FIFO(4) → strobe(0x35) → delay(600) → strobe(0x3B) → strobe(0x36)`（单发，无 SYNC 写入） |
| 原厂 TX2(ID=0) | `wake → delay(40) → FIFO(2) → strobe(0x35) → delay(500) → strobe(0x3B) → strobe(0x36)` |
| 补丁 TX4(ID=99) | `wake → SYNC=0xD798 → FIFO(4) → 35/600/3B/36 → wake → SYNC=0x01F4 → FIFO(4) → 35/600/3B/36 → SYNC=0xD798` |
| 补丁 TX2(ID=99) | `wake → SYNC=0xD798 → delay40 → FIFO(2) → 35/500/3B/36 → wake → SYNC=0x01F4 → delay40 → FIFO(2) → 35/500/3B/36 → SYNC=0xD798` |
| 补丁 TX4/TX2(ID=0/1/5/37/98) | 与原厂镜像**逐事件完全一致**（单发、无 SYNC 写入） |

- 双发第二帧同步字 `0x01F4 = floor(50024/100)`，即原厂 ID=99 同步字（兼容原厂灯）。
- 两帧的同步字写入都发生在对应 `wake` 事件之后（新版设计的关键点，已动态复核）。
- 双发使 2B 短命令每帧发射次数 `1 → 2`（时序影响见 §14）。
- 所有运行的 `SP` 回到初值、无 Unicorn 异常。

## 12. 已确认的“非问题”事实

- `0x0802E950/0x0802E962`（初始化表）写 reg4=`0xC3`/reg5=`0x68`，随后同步字函数按 ID 覆盖 —— 正常原厂流程。
- `0x0802F040` 函数尾是 `b.w delay_us(700)` 尾调用而非 `bx lr`，属于原厂代码风格，不影响边界判定（下一函数 `0x0802F09C`）。
- `0x0802F04A add r3,r2` 依赖函数头 `movs r2,#1`；`udiv` 为无符号，故公式 = `floor(50024/(ID+1))`；Unicorn 用 8 组 ID 复核。
- 入口 B.W 后残留的 2 字节原 `bl` 半字不会再执行（蹦床从 `+6` 恢复）。
- 注入区 `0x081C0000` 窗口在成品中只新增 3 个外部跳入，且注入区自身无外部数据引用。

## 13. 风险与未验证项（重要）

1. **无 X3 Pro 整机模拟器**：本验证是**调用级**（capstone 静态 + Unicorn 单函数 harness），
   **没有**整机 boot、主循环、中断/NVIC、菜单 UI、按键响应、射频状态机的运行验证。
   与项目内 V1C 等设备同级别证据，不能替代整机回归。
2. **无实机刷机验证**：未在真实 X3 Pro / 灯上刷入测试；官方 G3 升级软件是否接受此 bin、
   bootloader 是否校验 app/CRC/签名、刷入后配对/引闪/连拍行为均未验证。刷机风险由使用者承担，
   建议按项目安全阶梯先做小步验证。
3. **双发时序变化**：密钥模式下每个发送帧变成两次发射：
   - TX4（4B 帧）每帧多约 600 µs 发射 + 一次唤醒/同步字写入；
   - TX2（2B 短命令，原厂 D5 短命令还会连发 3 次）每帧多约 500 µs + 唤醒/同步字写入。
   按键响应、HSS/连拍、时序敏感协议是否受影响**未量化**。若实机异常，可先把模块内
   `DUAL_SEND` 关掉（只剩“密钥模式 = 全 KEY 单发”，普通灯不会被引闪）。
4. **注入窗口未关中断**：包装在两次发射之间切换 CC2500 同步字，注入代码**没有** `cpsid`；
   射频中断发送路径若在该窗口插入，可能出现同步字/忙标志竞态。原厂 `radio_wake` 会置忙标志
   `0x20001D09`、发射结束清忙，提供部分保护，但窗口（数十~数百 µs）未被证明无竞态。
5. **`set_sync` 用 burst 写 reg `0x44` 与原厂逐字节写 reg4/5 的差异**：CC2500 burst 会地址自增，
   理论上等价；未在硬件/整机模型验证。
6. **`radio_wake` 调用次数变化**：原厂每帧调用 1 次，双发每帧经两个蹦床共调用 2 次。
   静态看 `0x20001D06` 状态字节为 0 时只置忙并返回（无害）；为 1 时走 `cpsid` + SFTX/SIDLE + 20 µs + 清状态。
   极端中断时序下状态字节变化的副作用未验证。
7. **ID=99 语义占用**：打补丁后 ID=99 成为密钥模式，用户不能再把它当普通 ID 用；
   第二帧 `0x01F4` 是原厂 ID=99 同步字，**未打补丁**的灯需设为 ID=99 且同频道才能被兼容引闪。
8. **静态引用扫描局限**：字面量/分支扫描无法完全排除运行时通过 DMA、函数指针表或计算地址
   间接引用 `0x081C0000` 的可能；当前窗口静态零引用，且落在原厂 0xFF 区，风险低但非零。
9. **只验证了密钥 `0xD798`**：注入代码的 KEY 常量是参数化的，但脚本仅按 `0xD798` 成品验证；
   换密钥需用 `--key` 重跑（脚本支持）。
10. **基址证据为静态**：VTOR 写入 + 向量表一致性是强证据，但未用调试器/硬件读 PC 复核。
11. **热靴子镜像**：`0x081D4000` 起 24,092 B 子镜像未被修改（差异集合可证），但未做运行验证。

## 14. 与任务书 / Lead 描述的差异（均非代码 bug）

1. **注入区大小**：任务书写 176 B；重设计后实际为 **232 B（0xE8）**，预留窗口仍为 0x400。
   以最新成品与 `build_injection()` 实际输出为准（Lead 已说明）。
2. **调用点计数口径**：任务书 “16 / 9 个调用点” = **BL 调用点**；另有 2 / 1 个 `B.W` 尾跳
   （`0x0802CAF4`/`0x0802F126`、`0x0802CAD0`）也进入同一入口，总静态入口引用 18 / 10。
   入口本身被改写，不影响覆盖完整性。
3. **同步字函数边界表述**：任务书 “0x5A 字节，下一函数 0x0802F09C” —— 最后指令结束于
   `0x0802F09A`（= `0x0802F040 + 0x5A`），`0x0802F09A` 起 2 字节 NOP 对齐，下一函数入口 `0x0802F09C`（+0x5C）。
   补丁点 `0x0802F046`、`0x0802F050` 不受影响。
4. **ID 钳位地址表述**：任务书 “`0x08029996` 处 `cmp r3,#0x63`” —— `0x08029996` 是钳位代码块起始，
   实际 `cmp` 在 `0x080299A4`（`0x080299B2` 的 `b` 跳回该比较）；钳位上限 99 已用 Unicorn 片段实测。
5. **`keypatch/devices/x3pro.py` 文档注释（非代码逻辑）**：第 40 行 “0x5A 字节，下一个函数 0x0802F09C”、
   第 43–44 行 “set_sync 调用点 0x0802F226 / 0x0802F8F6 …（0x08029996 …）” 属旧口径描述（与上面 3/4 同理），
   建议后续顺手改成精确地址（`0x0802F230`/`0x0802F900` 读 ID、实际 `bl` 在 `0x0802F234`/`0x0802F902`）。

未发现与 Lead 结论相矛盾的事实，未发现补丁逻辑 bug。
