## 2. 固件身份与镜像基址（候选 #1：PASS）

- 长度 88032 字节、sha256 与给定值一致。
- 向量表（文件偏移 0）：
  - `[0] MSP = 0x20001550`：位于 RAM（0x2000_0000..0x2000_2000），8 字节对齐；
  - `[1] Reset = 0x080030D5`：Thumb 地址。
- Reset 处理函数（0x080030D4，即 `0x080030D5 & ~1`）：

```
0x080030D4  04 48        ldr  r0, [pc, #0x10]   ; [0x080030E8]=0x0801409D (SystemInit)
0x080030D6  80 47        blx  r0
0x080030D8  04 48        ldr  r0, [pc, #0x10]   ; [0x080030EC]=0x080030C1 (__main)
0x080030DA  00 47        bx   r0
```

- `__main` 桩位于 0x080030C0（文件偏移 0xC0），字节
  `03 48 85 46 00 f0 92 f9 00 48 00 47`，其 LDR 字面量 0x20001550
  **等于向量表 MSP**；由此反推基址 = `0x080030C0 - 0xC0 = 0x08003000`（自洽，不依赖假设）。
- 交叉验证：Reset 向量 0x080030D5 与已支持的 AD100 Pro / AD200 Pro 固件相同。
- 其余绝对引用（调用 0x080121BC 的 5 个 BL、0x080121F4 的调用点、辅助函数 BL 目标等）
  在该基址下全部落在镜像范围内并解码为合理代码。

## 3. 同步字函数身份、边界与字节（候选 #2：PASS）

- 函数 0x080121BC 起 56 字节，原厂内容与 Lead 给定值 **逐字节一致**：

```
0c4a10b5411c1046f0f794ff0446010a042003f07efae1b2052003f07afa
142003f030f9332003f0d5fa7d20c00003f029f910bd68c30000
```

- 顺序反汇编（从 0x080121BC 解码到 0x080121F0 停止）恰 20 条指令、52 字节代码；
  0x080121F0 处 4 字节字面量 = 0x0000C368 = 50024。
- 原函数 6 条 BL：
  - 0x080121C4 -> 0x080030F0（`__aeabi_uidiv`）
  - 0x080121CE -> 0x080156CE（`WriteReg(4, hi)`）
  - 0x080121D6 -> 0x080156CE（`WriteReg(5, lo)`）
  - 0x080121DC -> 0x08015440（`delay(20)`，r0=0x14）
  - 0x080121E2 -> 0x08015790（`strobe(0x33)` = SCAL）
  - 0x080121EA -> 0x08015440（`delay(1000)`，r0=0x7d<<3）
- 边界：0x080121F4 是真实函数起点（BL 调用点 0x0800DCE2），不是字面量/数据；
  除入口 0x080121BC 外没有任何 BL/分支目标落入 0x080121BC..0x080121F3；
  函数区字面量仅被 0x080121BC 的 LDR 引用（-> 0x080121F0）。因此 56 字节整段改写安全。

## 4. 辅助函数语义（候选 #5：PASS）

| 符号 | 地址 | 证据 |
|---|---|---|
| `__aeabi_uidiv` | 0x080030F0 | 22 条自包含循环（无 BL），`r0=商`、`r1=余`；Unicorn 保留真实执行 |
| `WriteReg(reg,val)` | 0x080156CE | `push {r0,r1,r4,lr}; movs r2,#1; add r1,sp,#4; bl 0x080157A8`，即把 `[sp+4]=r1(val)` 以 1 字节写入地址 `r0(reg)` |
| `strobe(cmd)` | 0x08015790 | `push {r4,lr}; mov r4,r0; bl 0x080157D4; mov r0,r4; bl 0x08015718`（命令写） |
| `delay(n)` | 0x08015440 | `subs r0,#1; uxth;` 内层 nop 循环，`bx lr`（r0=计数） |

## 5. 50024 字面量全局搜索

- 字节模式 `68 c3 00 00` 全镜像 **只出现 1 次**：文件偏移 0x0F1F0 = 地址 0x080121F0。
- 引用该字面量的 LDR 只有 0x080121BC（`ldr r2,[pc,#0x30]`）。
- 没有任何代码以立即数/其他形式直接使用 50024。
- 结论：原厂「ID -> 50024/(ID+1)」公式只存在于这一个函数中；补丁保留 50024
  在 +0x34 同址同值，不引入新的 50024 副本。

## 6. 全镜像 reg4/reg5 写路径（候选 #3：PASS）

全镜像 `BL -> WriteReg(0x080156CE)` 共 **59** 个调用点。对每个调用点做 r0 静态解析：

- 写 reg4/reg5 的调用点**恰为 4 个**：
  - 0x080121CE：`movs r0,#4`（原同步字函数 SYNC1）
  - 0x080121D6：`movs r0,#5`（原同步字函数 SYNC0）
  - 0x0801549E：`movs r0,#4; movs r1,#0xC3`（初始化表 SYNC1）
  - 0x080154A6：`movs r0,#5; movs r1,#0x68`（初始化表 SYNC0）
- 其余 55 个调用点 r0 为其他常量（另一处动态点 0x0800F9B8 为
  `movs r1,#0x18; mov r0,r1`，与 reg4/5 无关）。
- 底层单寄存器写 `0x080157A8` 的另外两个直接调用点写入 0x7E/0x7F，均非 4/5；
  第二个调用点 0x080156D4 在 WriteReg 内部、其 r0 来自 WriteReg 参数（已被上面的扫描覆盖）。
- 结论：除「同步字函数」与「CC2500 初始化表」外，镜像中**没有**其他代码写 SYNC1/SYNC0
  （也没有其它 API/立即数形式的旁路）。

## 7. 初始化表与 RF 初始化顺序（候选 #3：PASS）

- 0x08015470 是 CC2500 配置初始化表：**47 次 WriteReg，寄存器集合恰为 0x00..0x2E**
  （CC2500 配置寄存器区），其中：
  - 0x0801549E -> `WriteReg(4, 0xC3)`（SYNC1）
  - 0x080154A6 -> `WriteReg(5, 0x68)`（SYNC0）
- 该初始化表**只被 RF 初始化调用一次**：0x08006662（BL 0x08015470）。
- RF 初始化函数 0x0800664C 内部：0x08006662 先调用初始化表，0x080066B2 后调用
  同步字函数 0x080121BC（入参 = settings[6]）。
- 0x080066B2 没有其他分支目标可达（只能顺序执行），因此每次 RF 初始化都必然
  先写 0xC3/0x68、再被同步字函数覆盖。RF 初始化本身被 0x0801417C、0x08014A30 调用。
- 结论：补丁不改初始化表也安全；上电/重初始化时最终 SYNC 值由补丁函数决定。

## 8. 同步字函数 5 个调用点与 ID 入参（候选 #4：PASS）

全镜像 `BL -> 0x080121BC` 的调用点**恰为 5 个**（与 Lead 给出一致）：

| 调用点 | 所在函数 | 取 ID 指令 | 设置区基址来源（静态数据流） |
|---|---|---|---|
| 0x08006274 | 0x080061CC..0x0800664B | 0x08006272 `ldrb r0,[r0,#6]` | 0x0800620E `ldr r0,[pc,#0x3B8]` -> [0x080065C8]=**0x20001086** |
| 0x080066B2 | 0x0800664C..0x080066CF（RF init） | 0x080066B0 `ldrb r0,[r0,#6]` | 0x080066AE `ldr r0,[pc,#0x1C]` -> [0x080066CC]=**0x20001086** |
| 0x0800D484 | 0x0800D3D8..0x0800D8B7 | 0x0800D482 `ldrb r0,[r0,#6]` | 0x0800D41A `ldr r0,[pc,#0x3BC]` -> [0x0800D7D8]=**0x20001086** |
| 0x0800E0C2 | 0x0800DCDC..0x0800E19B | 0x0800E0C0 `ldrb r0,[r4,#6]` | 0x0800E06C `ldr r4,[pc,#0x98]` -> [0x0800E108]=**0x20001086** |
| 0x0800E138 | 0x0800DCDC..0x0800E19B | 0x0800E136 `ldrb r0,[r4,#6]` | 同上（r4 未被改写） |

即 5 个调用点在执行前 r0 = `*(uint8_t *)(0x20001086 + 6)` = `RAM[0x2000108C]`。
**补丁函数本身不依赖该 RAM 地址**：它只把入参 r0 当 ID 使用，56 字节内只有
KEY/50024 两个字面量，没有 0x20001086/0x2000108C 或任何设置区地址（已用独立构造的
两种 KEY 补丁字节逐字节确认；Lead 据此修正 `devices/v1c/README.md` 的调用点表是正确的）。

补充证据（settings[6] 就是 ID 设置字节）：

- 两个「C.Fn 改值」处理函数（0x080061CC / 0x0800D3D8）都有
  `cmp r1,#6; beq <同步字调用>` 门条件（0x0800625C/5E、0x0800D46E/70）：
  只有改动项 == 6（ID 项）才重设同步字。
- ID 菜单显示代码：0x08004EA2 读取当前 C.Fn 项（RAM 0x200004F2），
  `cmp #6` 命中后 0x08004EB0 `ldrb settings[6]`；ID!=0 时
  0x08004EB6 `movs r1,#0xa; bl __aeabi_uidiv`（/10 取十位），ID==0 走单独分支
  0x08004F2C（与数值 0..99 显示路径不同）。这是「ID=0 对应 OFF」的静态线索（仍未实机确认，见风险）。
- 设置持久化：0x08006004 载入设置区基址，0x08006026 读取 settings[6] 存入 flash 记录，
  说明 ID 本来就是随设置保存的字节，补丁不需要额外持久化改动。

### 8.1 对早期 `log_scan4.txt` 候选 RAM 地址的澄清（不是功能错误，但需更正）

`devices/v1c/re/log_scan4.txt` 曾把 0x200004F5（ID=0x200004FB）等列为「settings 基址候选」。
该脚本的回溯把 `ldrb r0,[rX,#6]` 的**目的寄存器 r0** 误当成基址寄存器 rX（代码取的是
`op_str.split(',')[0]`），因此候选值不可信。本审计用 CFG 前驱 + 反向数据流重新解析，
真实设置区基址是 **0x20001086**，ID 字节地址 **0x2000108C**。
Lead 结论 #4 的语义（入参都是 settings[+6]）不受影响；补丁函数本身也只接收 r0，不依赖该地址。

### 8.2 关于 0x08006274 附近「第二条数据流」的说明（避免误判）

0x08006292..0x080062AD 是 GCC `__gnu_thumb1_case_*` 分派 helper（0x080150A6）之后的
**switch 跳转表/内嵌数据**，线性反汇编会把它解码成指令（例如让 r0 来自
`ldrh r0,[r7,#0x12]`，若为真代码会访问非法地址 0x12 附近）。本审计的静态脚本
先用 switch helper 识别（0x080150A6）+ 函数内前向可达性剔除数据区，再做反向数据流，
得到唯一且正确的基址定义；简单线性回溯可能在此处产生虚假的 ambiguous。Unicorn 结果
也证明真实执行序列正确。

## 9. 拟采用补丁的静态构造（候选 #6：PASS）

Lead 设计在 0x080121BC 起 56 字节内整段改写：

```
sync = (id == 0) ? KEY : 50024/(id+1);
WriteReg(4, sync >> 8);   // SYNC1
WriteReg(5, sync & 0xFF); // SYNC0
delay(20);                // 保留原厂 20us 建立时间
return;                   // 去掉 SCAL(0x33) + delay(1000)
```

独立构造的布局（与 DESIGN_TOGGLE v2 / AD200 v2 一致）：

```
+0x00..+0x2F  48 字节代码（20 条 Thumb 指令，含 4 条 BL）
+0x30         4 字节字面量 KEY          （0x080121EC）
+0x34         4 字节字面量 50024        （0x080121F0，与原厂字面量同址同值）
```

静态验证结果：

- 长度 56，结束于 0x080121F4 == 下一函数起点，不越界；
- 代码结束于 +0x30（0x080121EC），与字面量无重叠；
- BL 目标 = `uidiv, WriteReg, WriteReg, delay`；含 `movs r0,#0x14; bl delay`；
  不含 `movs r0,#0x33` / `0x7d<<3`；
- 补丁后镜像长度不变；与原厂差异 48 字节，全部落在 0x0F1BC..0x0F1F3；
  0x080121F0 的 50024 不变；
- KEY=0xD798 / 0xA5C3 各自构造通过。

补丁字节（KEY=0xD798）：

```
0b4a10b5002802d00a4a411c00e001211046f0f78fff0446010a042003f079fae1b2
052003f075fa142003f02bf910bd98d7000068c30000
```

（KEY=0xA5C3 仅 +0x30 字面量不同：`c3a50000`。）

## 10. Unicorn 调用级验证（候选 #6 行为级：PASS）

harness 设置：映射 0x08000000..0x08020000（镜像）、0x20000000..0x20004000（RAM/栈）；
从 `0x080121BC|1` 执行，r0=ID；WriteReg/strobe/delay 入口写 `bx lr` 桩并用 code hook
记录参数；**`__aeabi_uidiv` 保留真实代码执行**（保证除法真实发生）；返回哨兵 `b .`。

### 10.1 原厂镜像自证（全部 PASS）

| ID | 期望 sync = 50024//(ID+1) | 实际调用序列 |
|---|---|---|
| 0 | 0xC368 | WriteReg(4,0xC3) -> WriteReg(5,0x68) -> delay(20) -> strobe(0x33) -> delay(1000) |
| 1 | 0x61B4 | WriteReg(4,0x61) -> WriteReg(5,0xB4) -> delay(20) -> strobe(0x33) -> delay(1000) |
| 5 | 0x2091 | WriteReg(4,0x20) -> WriteReg(5,0x91) -> delay(20) -> strobe(0x33) -> delay(1000) |
| 37 | 0x0524 | WriteReg(4,0x05) -> WriteReg(5,0x24) -> delay(20) -> strobe(0x33) -> delay(1000) |

原厂 ID=0 得到 50024（不是 KEY），证明「ID=0 -> KEY」确实是补丁新增语义。

### 10.2 补丁镜像（KEY=0xD798 / 0xA5C3 各一遍，全部 PASS）

**需要 Lead 注意的两点（不影响补丁正确性）：**

1. **旧 `log_scan4.txt` 的 RAM 基址候选是错的**（回溯 bug，把目的寄存器当基址），
   如果有人按 0x200004F5 去写/核对「设置区」，会得到错误结论；真实 ID 字节地址是
   0x2000108C。补丁函数不需要知道该地址（ID 由调用者传入），因此不影响实现。
2. **「与 AD100 id0 版一致」仅指语义**：AD100 的 `build_sync_function_id0()` 实际是
   44B 代码、KEY 在 +0x2C、**不保留 delay(20)**；本 V1C 设计是 48B 代码 + delay(20)，
   KEY 在 +0x30、50024 在 +0x34（与 DESIGN_TOGGLE v2 / AD200 v2 一致）。

## 12. 风险与未验证事项（必须随补丁交付说明）

1. **无实机验证（最高风险）**：本轮只有静态复核 + Unicorn 单函数调用级验证；
   没有整机模拟、没有真实 V1C + 虚拟/真实 CC2500 的 RF bring-up，更没有任何真机刷写。
   发布前必须用真机验证：
   - 刷入 V1C 补丁固件 + 配套已打补丁的引闪器（同一 KEY），确认能引闪/收包；
   - 上电后第一次收包（对应下面的 SCAL 风险）；
   - ID 菜单在 0/1/5/37/99 之间切换、掉电重上电后 ID 保持；
   - 与未打补丁的原厂灯/引闪器混用时的兼容性（普通模式应与原厂一致）。
2. **去掉 SCAL(0x33) + delay(1000) 的影响**：SCAL 是 CC2500 频率合成器校准命令；
   本补丁只改 SYNC1/SYNC0（纯数字同步字），不改 FREQ2/1/0、不改信道，
   且 RF 初始化路径本身已执行过 SCAL；保留 20us 建立时间与 AD200 v2 的既有分析一致。
   但这是相对原厂**唯一**的射频行为差异：若某批次 CC2500/兼容芯片要求写 SYNC 后
   重新校准，极端情况可能「上电首包丢失」。真机若出现首包丢失，优先怀疑此点；
   56 字节原位空间无法同时容纳「ID==0 分支 + SCAL + 1ms」（实测 48B 代码已用满），
   届时需把函数整体搬到空闲 flash 注入区再保留 SCAL/延时。
3. **ID==0 是否真是用户可见的 OFF（未实机/未 UI 模拟确认）**：静态线索支持
   （C.Fn 项 6 = ID；ID!=0 走 /10 数值显示，ID==0 走单独显示分支 0x08004F2C），
   但本审计**没有** UI 截图、菜单字符串或实机确认。因此「ID 菜单设 0（OFF）即密钥模式」
   是**设计约定**而非已证事实；若实际固件的 ID 菜单把 0 显示成 `0` 或不允许 0，
   用户将无法通过 ID 菜单开启密钥模式（此时需改用 C.Fn 标志版方案）。
   此外 ID=0 在原厂普通模式下等价于 50024；补丁后该值被替换为 KEY，
   老用户若把 ID 设为 0 会突然进入密钥模式，需要文档明确告知「ID=0 语义已改变」。
4. **ID 必须由补丁引闪器配套**：灯端密钥模式只接受 KEY 同步字；引闪器必须用同一 KEY
   （X3-C / AD100 / AD200 的既定方案）；KEY 建议取大于 50024 的值（如 0xD798/0xA5C3），
   否则可能与某个 `50024//(ID+1)` 普通值相同，导致普通灯误触发/密钥灯被普通帧触发。
5. **补丁只覆盖 5 条已定位的「ID -> 同步字」调用路径**：RF 初始化 1 条 + C.Fn 改值
   处理 2 条 + 远程/设置处理 2 条。若其他未识别路径直接改写 SYNC 寄存器（本镜像静态
   扫描未发现），或未来固件版本增加新路径，需要重新复核。补丁模块应在打补丁前严格校验
   原厂 56 字节（与本报告 §3 的字节一致），版本不符时拒绝打补丁。
6. **固件版本锁定**：本审计只对 `V1C_V2.0.bin`（sha256 4435dd…edfb）有效；
   任何其它 V1C 固件（V2.1 等）必须重新审计地址/字节/调用点。
7. **静态反汇编注意事项（供后续复核者）**：capstone 必须 `skipdata=True`；
   0x08006620 附近、0x08006292..0x080062AD、0x080121F0 等位置有字面量/跳转表；
   `__gnu_thumb1_case_*` helper 0x080150A6 之后的 BL 不按普通调用返回，
   简单线性回溯会产生虚假控制流（见 §8.2）。`audit_static.py` 已内置这些处理。

## 13. 结论

对 `V1C_V2.0.bin` 的独立静态 + Unicorn 复核表明：Lead 的补丁点定位（基址、函数地址/
56 字节边界、原厂字节、唯一 SYNC 写路径、初始化覆盖顺序、5 个 ID 调用点、辅助函数）
全部成立；按设计手工构造的 56 字节补丁在调用级行为上完全符合预期
（ID=0 -> KEY；ID=1..99 -> 原厂公式；无 SCAL/1ms，保留 delay(20)）。
