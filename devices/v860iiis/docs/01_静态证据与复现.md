# V860III-S 静态证据与复现（补丁点定位过程）

本文记录 V860III-S（`V860IIIS_V1.1.bin`）补丁点的定位过程与可复现脚本，供复核/换版本时重新定位用。
结论已汇总进 [`../README.md`](../README.md)，这里只放**过程证据**与**复核操作**。

> 前置：仓库根便携 Python `tools\python\python.exe`（capstone 5.0.7 / unicorn 2.1.4）；
> 固件 `devices/v860iiis/firmware/V860IIIS_V1.1.bin`（79,300 B，sha256 `bdc8f354…0b20`）。
>
> 本文按 **v1（C.Fn `LIGHT` 开关，2 字节 NOP 即时生效）** 编写。
> V860III-S 的 C.Fn **不显示 F1..F12 编号**，菜单里只有名称；本机型 UI 只有 10 项。
>
> ⚠️ 全文为**离线静态/Unicorn 证据**；无实机验证。

## 1. 定位方法（从常量 50024 = 0x0000C368 入手）

1. 在镜像里搜 4 字节小端字面量 `68 c3 00 00`（= 50024）；
2. 找到引用它的 `ldr r2, [pc, #imm]`，回溯到函数入口；
3. 反汇编该函数：应能看到
   `adds r1, r0, #1`（除数 = ID+1）→ `bl __aeabi_uidiv` → 两次 `WriteReg(4/5, …)` →
   `delay(20)` → `strobe(0x33)`（SCAL）→ `delay(1000)`；
4. 确认「全镜像只出现一次 `0xC368` 字面量」且「只有该函数与初始化表在运行期写寄存器 4/5」。

V860III-S 的结果：

| 项 | 值 |
|---|---|
| 50024 字面量 | 文件偏移 `0x0E5EC` / VA **`0x080115EC`**，全镜像唯一 |
| 引用指令 | `0x080115B8 ldr r2,[pc,#0x30]`（字节 `0c 4a`），全镜像唯一引用 |
| 同步字函数入口 | **`0x080115B8`** |
| 下一函数 | **`0x080115F0`**（`0x0800CD80` 处有 `bl 0x080115F0`；函数体止于 `0x08011618 bx lr`） |
| 函数体长度 | **56 字节**（`0x38`） |
| 字面量位置 | `+0x34` = `0x080115EC`（与原厂同址同值保留） |

## 2. 复现脚本（可直接粘贴）

### 2.1 一行版：CLI 打补丁 + 校验

```powershell
# 仓库根
$env:PYTHONIOENCODING='utf-8'
tools\python\python.exe keypatch\keypatch.py info --device v860iiis
tools\python\python.exe keypatch\keypatch.py patch --device v860iiis --key 0xD798 --verify --out %TEMP%\kp_v860iiis
```

期望：`verify()` 输出 **73 × `[PASS]` / 0 × `[FAIL]`**，产物 79,300 B。

### 2.2 反汇编 + 调用点 + 写点扫描（Python 内联脚本）

```powershell
# 仓库根；打印同步字函数反汇编、5 个 BL 调用点、写 reg4/5 的 WriteReg 调用点
tools\python\python.exe -c @"
import struct, sys
sys.path.insert(0, 'keypatch')
from capstone import Cs, CS_ARCH_ARM, CS_MODE_THUMB, CS_MODE_MCLASS, CS_MODE_LITTLE_ENDIAN
BASE = 0x08003000
data = open(r'devices/v860iiis/firmware/V860IIIS_V1.1.bin', 'rb').read()
md = Cs(CS_ARCH_ARM, CS_MODE_THUMB | CS_MODE_MCLASS | CS_MODE_LITTLE_ENDIAN)
o = lambda a: a - BASE

print('== 同步字函数 0x080115B8（56 B）==')
for ins in md.disasm(data[o(0x080115B8):o(0x080115B8)+56], 0x080115B8):
    print('  0x%08X  %-12s %s %s' % (ins.address, ins.bytes.hex(' '), ins.mnemonic, ins.op_str))
print('原厂 56 B =', data[o(0x080115B8):o(0x080115B8)+56].hex(' '))

md.skipdata = True
insns = list(md.disasm(data, BASE))
by = {ins.address: i for i, ins in enumerate(insns)}
print('== BL -> 0x080115B8 ==')
for ins in insns:
    if ins.mnemonic == 'bl' and ins.op_str.strip() == '#0x80115b8':
        print('  caller 0x%08X' % ins.address)
print('== 写寄存器 4/5 的 WriteReg(0x08013926) ==')
for i, ins in enumerate(insns):
    if ins.mnemonic == 'bl' and ins.op_str.strip() == '#0x8013926':
        for back in range(1, 6):
            p = insns[i - back]
            if p.mnemonic in ('movs', 'mov') and p.op_str.startswith('r0, #'):
                if int(p.op_str.split('#')[1], 16) in (4, 5):
                    print('  0x%08X reg=%s（回溯 0x%08X）' % (ins.address, p.op_str.split('#')[1], p.address))
                break
"@
```

## 3. 关键证据表

### 3.1 同步字函数原厂反汇编（摘要）

见 [`../README.md`](../README.md) §2.1；核心 4 点：

1. `adds r1, r0, #1` → `bl __aeabi_uidiv(0x080030F0)`：`50024/(ID+1)`；
2. `lsrs r1, r0, #8` + `movs r0, #4` → `WriteReg(4, SYNC1)`；`uxtb r1, r4` + `movs r0, #5` →
   `WriteReg(5, SYNC0)`（`CC2500_WriteReg = 0x08013926`）；
3. 收尾 `delay_us(20)`（`0x08013698`）→ `strobe(0x33)`（`0x080139E8`，SCAL）→ `delay_us(1000)`；
4. `+0x34` 是 `50024` 字面量（全镜像唯一）。

> 交叉证据：`re/log_sync_audit.txt` §3 把 56 B 逐条复核（20 条指令 + 字面量），并确认
> 函数内部没有任何分支/调用目标；入口 `0x080115B8` 被 5 个 `BL` 指向。

### 3.2 5 个调用点（全部位于同一镜像，入参都是 `settings[6]`）

| 调用点 | 所在函数 | 取参指令 | settings 基址来源 | 触发路径 |
|---|---|---|---|---|
| `0x08005A78` | C.Fn 递减 handler `0x080059E4` | `0x08005A76 ldrb r0,[r0,#6]` | `0x08005A26 ldr r0,[pc,#0x330]` → `0x20001058` | 主循环 `0x08013CE4` → 键事件分发 `0x080058E4`（事件 `0x78`）→ handler |
| `0x08005E36` | RF 初始化函数 `0x08005DD0` | `0x08005E34 ldrb r0,[r0,#6]` | `0x08005E32 ldr r0,[pc,#0x1c]` → `0x20001058` | 整机初始化 `0x08012364` → RF 初始化 `0x08005DD0`（**无 `cmp #6` gate**） |
| `0x0800C5C2` | C.Fn 递增 handler `0x0800C528` | `0x0800C5C0 ldrb r0,[r0,#6]` | `0x0800C56A ldr r0,[pc,#0x36c]` → `0x20001058` | 主循环 `0x08013CE4` → 键事件分发 `0x080058E4`（事件 `0xB4`）→ handler |
| `0x0800D0BA` | RF 消息 handler `0x0800CD7C`（设置复位分支） | `0x0800D0B8 ldrb r0,[r4,#6]` | `0x0800D094 ldr r4,[pc,#0xc4]` → `0x20001058` | 主循环 `0x08013CE4` → 事件分派 `0x0800CD7C` |
| `0x0800D0E6` | 同上（恢复出厂分支 `bl 0x08005E54` 之后） | `0x0800D0E4 ldrb r0,[r0,#6]` | `0x0800D0E2 ldr r0,[pc,#0x78]` → `0x20001058` | 同上 |

补丁函数只接收 `r0`（ID），**不依赖**这个 RAM 地址；LIGHT 开关字节 `0x20001060` 由补丁函数内的字面量直接给出。
证据：`re/log_sync_audit.txt` §5（每个调用点都做「前一条 = `ldrb r0,[…,#6]`」+「基址载入后 r0 未被改写」断言；
其中递减 handler 的「1 处改写」是另一分支的 `0x08005A60 movs r0,#9`，审计脚本按严格口径记为 FAIL，见 §3.9）。

### 3.3 写寄存器 4/5 的全部位置（全镜像扫描）

| 调用点 | 写入寄存器 | 场景 |
|---|---|---|
| `0x080136F6` / `0x080136FE` | 4 / 5 | CC2500 初始化表（`0xC3/0x68` 缺省值，随后被覆盖） |
| `0x080115CA` / `0x080115D2` | 4 / 5 | 同步字函数（**唯一运行期写入**） |

全镜像 `CC2500_WriteReg(0x08013926)` 调用点共 **60 个**（初始化表占 47 个，寄存器号 `0x00..0x2E` 各一次），
所有调用点的 `r0`（寄存器号）都能静态解析，**写 4/5 的恰为上述 4 个**；底层写函数 `0x08013A00`
的直接调用点里也没有 reg4/5。证据：`re/log_sync_audit.txt` §6。

### 3.4 初始化覆盖顺序

```text
RF 初始化函数 0x08005DD0（初始化表入口 0x080136C8，被 0x08005DE6 调用一次）
  ├─ 初始化表：WriteReg(0..0x2E)，其中 0x080136F6 写 SYNC1=0xC3、0x080136FE 写 SYNC0=0x68
  ├─ WriteReg(0x3E, …)  PATABLE
  ├─ strobe(0x33) + delay_us(1000)
  └─ bl 0x080115B8（0x08005E36）  → 按当前 ID（及 LIGHT 开关）覆盖 SYNC1/SYNC0
```

所以只改 `0x080115B8` 就能覆盖全部设置路径。

### 3.5 C.Fn 设置区与开关项（`settings[8]` = LIGHT）

来源：`re/cfn_settings.py` + [`CFN_SETTINGS.md`](../../../keypatch/dev/v860iiis/CFN_SETTINGS.md)、
`re/cfn_menu.py` + [`CFN_MENU.md`](../../../keypatch/dev/v860iiis/CFN_MENU.md)。

- 设置区基址 **`0x20001058`**：item n = `settings[n]`；全镜像 **30 处 u32 字面量、42 条 `LDR` 引用**；
  ID = `settings[6]` = `0x2000105E`；本补丁开关 = **`settings[8]` = `0x20001060`**（C.Fn 第 3 页第 1 行 `LIGHT`）；
- 最大值/回绕表 **`0x08016102`**，12 字节 `01 01 01 01 01 1F 63 01 02 06 01 01`
  → max = `1,1,1,1,1,31,99,1,2,6,1,1`；3 个 LDR 引用：`0x08005A6A`（递减）、`0x0800C586`（递增）、
  `0x0800F086`（加载后钳位：`settings[i] > max[i] → settings[i]=0`，`cmp r0,#0xC` 12 项）；
- **item8 = LIGHT（原厂造型灯模式，三档 `12sec/OFF/ON` = `0/1/2`）**：
  出厂默认 **0（12sec）**（写点 `0x08005EB0` `strb r1,[r0,#8]`，`r1=0`）；
  功能读者 **`0x08003956` / `0x0800397E`**（造型灯任务 `0x08003950` 控制 GPIO `0x48001000` bit13/14）；
  菜单显示读者 `0x08004A8A` / `0x08004A9A`；save builder 读者 `0x08005816`；
  写者共 3 处：出厂默认 `0x08005EB0`、RF 复位 `0x0800D0A2`、load 展开 `0x08013C48`；
- **本机型 UI 只有 10 项（item 0..9）**：`m/ft, AF, STBY, RX STBY, SCAN, CH, ID, BEEP, LIGHT, LCD`
  —— 即 V1C 12 项的前 10 项；`FEB ACL`/`TX` 在本机型**不存在**（无菜单入口、无功能读者）。
  菜单 3 页 × 4 行，第 3 页只占前 2 行（LIGHT、LCD）；
- 项名/显示形式：**不显示 F 编号**，只显示名称；项名由真实执行渲染函数重建（字形表 `0x080143D6`，17 B/字形）；
- 注意：item10/11 只存在于 settings 字节与 72 B 持久化记录中（平台共用结构），
  **不要按「12 个可编辑 C.Fn 项」描述本机**。

### 3.6 补丁点的原厂字节（`apply()` 逐字节校验基准）

| # | 地址 | 原厂字节 | 补丁后（key 无关） | 说明 |
|---|---|---|---|---|
| 1 | `0x080115B8..0x080115EF` | `0c 4a 10 b5 41 1c 10 46 f1 f7 96 fd 04 46 01 0a 04 20 02 f0 ac f9 e1 b2 05 20 02 f0 a8 f9 14 20 02 f0 5e f8 33 20 02 f0 03 fa 7d 20 c0 00 02 f0 57 f8 10 bd 68 c3 00 00` | 见 [`../README.md`](../README.md) §2.3 | 56 B 整段改写（44 B 代码 + KEY/FLAG/50024 三个字面量） |
| 2 | `0x08005A74` | `02 d1` | `00 bf` | 递减 handler gate：`bne` → `nop` |
| 3 | `0x0800C5BE` | `f5 d1` | `00 bf` | 递增 handler gate：`bne` → `nop` |
| 4 | `0x08003956` | `00 7a` | `00 20` | 造型灯读者 1：`ldrb r0,[r0,#8]` → `movs r0,#0` |
| 5 | `0x0800397E` | `01 7a` | `00 21` | 造型灯读者 2：`ldrb r1,[r0,#8]` → `movs r1,#0` |
| 6 | `0x0800D0A2` | `26 72` | `00 bf` | RF 设置复位写 `settings[8]` → `nop` |

差异统计：同步字函数区 49 B + gate 4 B + 读者 3 B + 写者 2 B = **58 B**；其余字节与原厂完全一致。

### 3.7 代码洞评估（为什么本机不用注入）

- 全镜像**没有任何 ≥16 B 的 `0xFF` 擦除态区间**（`re/log_sync_audit.txt` §7）；
- ≥16 B 的全 0 区间共 27 个，绝大多数位于被引用的数据块（图形/查表数据）内部；
- 唯一「零引用且不在被引用数据块内」的是**向量表保留槽 `0x08003010`（28 B，ARMv6-M Reserved 异常，
  硬件永不取用）**——但它改的是向量表，且只有 28 B；
- `0x080162B9` 起 112 B 零区零引用，但位于数据段尾部 `0x08016000` 之后的 LUT 数据表内，
  `0x08016328` 还被真实代码作为数据指针引用 → **最多算「条件可用」**，不能作为正式补丁的代码洞；
- 结论：**不用代码洞**；2 字节 `bne→nop` 已能达到「改任意项立即重设同步字」的效果，
  且已用 Unicorn 证明与 V1C 式 `BL` 注入方案行为等价（`re/log_cfn_settings.txt` §5/§9）。

### 3.8 内核/基址证据

来自 `re/log_sync_audit.txt` §1/§2：

- Reset 桩 `0x080030D4`：`ldr r0,[pc]; blx r0; ldr r0,[pc]; bx r0`，
  字面量 `0x080030E8 = 0x08011B29`（SystemInit）、`0x080030EC = 0x080030C1`（`__main`）；
- `__main` 桩 `0x080030C0`：`03 48 85 46 00 f0 7c f9 00 48 00 47`，
  `ldr` 字面量 `0x080030D0 = 0x20001548` == 向量[0] SP → 反推 **base = 0x08003000**；
- 内核：干净函数体 11,428 条指令 / 447 个函数中，32 位非 `BL` 指令 **0** 条；
  全镜像 857 条 4 字节指令**全部是 `BL`**；M4 特征指令在真实函数体内 **0** 条
  → **Cortex-M0 / ARMv6-M（Thumb-1）**，Unicorn 用 `UC_ARCH_ARM + UC_MODE_MCLASS`。
  （`re/recon1.py` 早期把 `bl` 误计为「M0 不支持的 32 位指令」，已在此更正。）

### 3.9 独立审计结论（`sync_audit.py` / `SYNC_AUDIT.md`）

`re/sync_audit.py` + [`SYNC_AUDIT.md`](../../../keypatch/dev/v860iiis/SYNC_AUDIT.md) 的独立审计
**132 PASS / 0 FAIL**（退出码 0；另 Unicorn 5 个 ID 共 30 项断言 PASS），逐条确认：

| 待验证结论 | 结果 |
|---|---|
| base = `0x08003000`（Reset 桩 + `__main` 桩 + 向量[0] 反推自洽） | PASS |
| 内核 Cortex-M0 / ARMv6-M（447 函数 / 11,428 条干净函数体指令中 32 位非 `BL` = 0） | PASS |
| 同步字函数 `0x080115B8..0x080115EF` 56 B；`+0x34` 字面量 50024 | PASS |
| **下一函数 = `0x080115F0`**（`0x0800CD80` 有 `bl 0x080115F0`，函数体止于 `0x08011618 bx lr`） | PASS |
| 5 个调用点入参来自 `settings[6]`（CFG 路径集合证明基址恒为 `0x20001058`） | PASS |
| 60 个 `WriteReg` 中恰 4 个写 reg4/5；初始化表 47 写 reg `0x00..0x2E`，先 `0xC3/0x68` 后被覆盖 | PASS |
| 代码洞：无静态可证安全区（27 个 ≥16B 全 0 区、无 0xFF 区；候选 `0x080162B9` 属「条件可用」） | PASS（预期负结论） |
| Unicorn 调用级：`50024/(ID+1)` → `WriteReg(4,hi)` / `WriteReg(5,lo)` / `delay(20)` / `strobe(0x33)` / `delay(1000)` | PASS |

> 说明：脚本**首轮**运行曾报 6 项 FAIL（126 项），均为其自身判定口径问题
> （uidiv/strobe/delay_us 的函数体判定、「r0 未被改写」把另一分支 `0x08005A60 movs r0,#9`
> 计入、`0x080162B9` 零区按严格死区口径记 FAIL）；**修订版 132 项全 PASS**。
> 另：独立审计确认 **Lead 初勘写的「下一函数 `0x080115F4`」是笔误，应为 `0x080115F0`**
> （`0x080115F4` 无任何 `BL`/向量目标）——本次文档统一按 `0x080115F0` 书写。
