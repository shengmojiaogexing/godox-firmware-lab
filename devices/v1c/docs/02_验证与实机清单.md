# V1C 验证记录与实机清单

本文是 V1C 补丁（v5：**C.Fn 第 3 页 `LIGHT` 开关**）的**验证记录（离线）**与**实机测试清单**。
逆向结论与补丁规格见 [`../README.md`](../README.md)。

> ⚠️ 现状（2026-11-11）：**离线 verify 36 项 PASS、selftest ALL PASS；整机模拟器未建立；实机未验证。**

---

## 1. 离线验证：`verify()` 做了什么（36 项）

[`keypatch/devices/v1c.py`](../../../keypatch/devices/v1c.py) 的 `verify(patched, key)` 分四层、共 **36 项**：

| 层 | 项数 | 断言 | 说明 |
|---|---|---|---|
| 静态-函数 | 4 | 长度 88,032 B；同步字函数 56 B 与期望一致；结束于 `0x080121F4` 不越界；三个字面量（KEY/FLAG/50024）落位 | 原位补丁 + 边界 |
| 静态-新增补丁点 | 6 | 注入代码 @`0x08017944`；两个 gate（`0x0800625C`/`0x0800D46E`）已是 `BL` 注入；三个读者/保护点（`0x080036DA`/`0x08003702`/`0x0800A6FA`） | v5 新增的 6 处补丁点 |
| 静态-差异范围 | 2 | 与原厂差异集合 ==（7 处补丁点，共 71 B）；差异之外 0 处 | 证明没有改到别处 |
| Unicorn-补丁版 | 14 | 说明行 1 + flag=2（LIGHT=ON）ID=0/5/99 → KEY（3）+ flag=0/1（12sec/OFF）ID=0/1/5/37/99 → 原厂公式（10） | Cortex-M0 直接执行补丁后机器码，桩替换 WriteReg/strobe/delay |
| Unicorn-注入 hook | 5 | item=6(ID)/8(LIGHT)/5/8/11 改值 → 各调用同步字函数 1 次、r0=ID、r0..r4 原样恢复 | C.Fn 改值即时生效 |
| Unicorn-原厂自证 | 5 | 同一 harness 跑原厂函数（ID=0/1/5/37/99）→ 原厂公式 + `delay(20)+SCAL(0x33)+delay(1000)` | 证明「补丁只改了该改的」 |

复现命令：

```powershell
# 仓库根
tools\python\python.exe keypatch\keypatch.py patch --device v1c --key 0xD798 --verify --container --out %TEMP%\kp_v1c

# 总自检（4 台设备）
tools\python\python.exe keypatch\selftest.py --key 0xD798
```

实测结果：`patch --verify` **36 项全部 PASS**；`selftest.py` 结论 **ALL PASS**（ad100 / ad200 / x3c / v1c）。
产物：`V1C_V2.0_keyD798.bin`（88,032 B，sha256 `86d563c8…`）、
`V1C_V2.0_keyD798_container.bin`（88,088 B，sha256 `e1634a08…`）。

> 密钥换成别的值后 sha256 会变，需重新生成；`verify()` 对任意合法密钥都成立。

## 2. 离线验证覆盖不到的部分

1. **整机启动/主循环**：V1C 没有整机模拟器，启动链/外设/看门狗未回归；
2. **空口同步过滤**：Unicorn 只验证「写了正确的 SYNC1/SYNC0」，真正的射频同步必须真机；
3. **C.Fn 菜单/显示**：第 3 页第 1 行 **`LIGHT`**（固件不显示 F 编号；3 页 × 4 行）是否存在、
   可选中/改值、掉电保存，未实机确认。UI 报告 `CFN_MENU.md` 通过渲染函数重建确认右栏为
   `12sec / OFF / ON`（对应 `0/1/2`），**显示极性需实机最终确认**；
4. **造型灯行为**：原厂 LIGHT 三档控制造型灯模式；补丁把两个功能读者固定为 0（12sec），
   需确认造型灯输出与预期一致；
5. **无线设置同步覆盖**：v5 已 NOP `0x0800A6FA`（紧凑解包写 `settings[8]`），
   但 `0x0800DCDC` 路径仍会整体写设置区，需实测；
6. **持久化**：`settings[8]`（LIGHT 值 0/1/2）重启后是否保持（依赖原厂 flash 记录保存/加载）；
7. **显示/UI**：本轮完全没碰 UI/字库，只复用原厂 C.Fn 菜单项。

## 3. 实机测试清单（风险自负，按顺序做）

前置：官方 G3 能识别设备；手上有 `devices/v1c/firmware/V1C_V2.0.bin` 可回滚。
> 判定口径：补丁只看 **`settings[8]`**（C.Fn 第 3 页 `LIGHT` 的值）。
> **`LIGHT = ON`（值 2）= 密钥模式**；`12sec`（值 0，出厂默认）/`OFF`（值 1）= 原厂普通模式。

- [ ] 刷 `V1C_V2.0_keyD798.bin` 后能正常开机、菜单显示正常、版本号仍是 V2.0；
- [ ] 进 **C.Fn 菜单**确认第 3 页第 1 行 **`LIGHT`**（不显示 F 编号），可在 `12sec/OFF/ON` 三档间切换；
      新刷/恢复出厂后应为 `12sec`（值 0）；
- [ ] **普通模式**：`LIGHT = 12sec`（或 `OFF`），ID=1..99，与同 CH/ID 的原厂引闪器/灯能正常引闪；
- [ ] **密钥模式**：`LIGHT = ON` + 已打补丁的引闪器（同一把 0xD798）→ 能引闪；
- [ ] **隔离验证**：引闪器切回普通模式后，`LIGHT = ON` 的灯**不被引闪**；
- [ ] **即时生效**：不动其它设置，仅来回切 LIGHT `ON ↔ 12sec`，确认同步字立即切换（可用配对/未配对引闪器验证）；
- [ ] **造型灯（LIGHT 代价）**：确认造型灯输出保持原厂 `12sec` 档行为；C.Fn 里改 LIGHT 不再改造型灯模式；
- [ ] **持久化**：重启设备后 `LIGHT` 仍为 `ON`（密钥模式）；恢复出厂后回到 `12sec`（普通模式）；
- [ ] **无线设置同步覆盖检查**：用 G3/引闪器做一次「设置同步/远程设置」，确认 `settings[8]` 不被清回 0/1；
- [ ] 改 ID 菜单来回切几次，确认普通模式下每次同步字都跟着变（hook 不破坏原厂 ID 行为）；
- [ ] 任意异常 → 立刻刷回原厂（[`keypatch/README.md`](../../../keypatch/README.md) §刷机/回滚）。

### 3.1 异常排查提示

| 现象 | 优先怀疑 | 处理 |
|---|---|---|
| 密钥模式下偶发首包丢失 | 删掉的 `SCAL+1ms` 与 `delay(20µs)` | 保留原厂 strobe/延时序列的变体（见 `devices/v1c/README.md` §6.6） |
| 密钥模式完全不响应 | 引闪器是否也打了同一把密钥 / `settings[8]` 是否真为 2 且已保存 | 先确认引闪器侧与开关值 |
| LIGHT 值一开机又变回 0 | 无线设置同步覆盖 `settings[8]`（`0x0800DCDC` 路径） | 记录现象，需补丁进一步保护该写点（待办） |
| 造型灯不亮/行为异常 | 造型灯读者屏蔽（`0x080036DA`/`0x08003702`）副作用 | 对照原厂刷回确认，必要时回退该 2 字节 |
| 普通模式异常 | 补丁点越界或固件版本不符 | 核对 sha256 / 各补丁点原始字节，重新生成 |
| 刷坏后 G3 找不到设备 | — | 先正常开机 → 按一下侧拨轮 → 插 USB（救砖流程见 keypatch/README） |
