# X3 Pro S 验证与实机清单

本文是 X3 Pro S 补丁（**ID=99 = 密钥模式 + 兼容双发**）的**离线验证清单**与**实机测试清单**。
逆向结论与补丁规格见 [`../README.md`](../README.md)；静态证据见
[`01_静态证据与补丁点.md`](01_静态证据与补丁点.md)。

> ⚠️ 现状（2026-11-11）：**只有离线静态检查 + Unicorn 调用级验证；整机模拟器未建立；实机未验证。**
> 离线 `verify()` 的**具体项数与 PASS 数不固化在本文档**，以实际运行
> `keypatch.py patch --device x3pros --verify` 的输出为准（项数可能随模块实现调整）。

## 1. 离线验证项清单

### 1.1 分层与判定口径

| 层 | 检查什么 | 期望 | 说明 |
|---|---|---|---|
| 静态-镜像身份 | 长度、sha256 | 长度 **1,931,868 B**；sha256 与原厂一致（补丁前） | `apply()` 在打补丁前硬校验；不一致直接拒绝 |
| 静态-补丁点 | 3 个入口 + 注入区字节 | `0x0802F0C6` 10 B、`0x0802EE44`/`0x0802EEAC` 各 4 B 与模块期望一致；注入区代码一致、剩余仍 `FF` | `verify()` 逐字节断言 |
| 静态-差异范围 | 与原厂差异集合 | 差异**只**落在补丁点 + 注入区；差异之外 **0 处** | 用集合比对断言，防误改其它字节 |
| Unicorn-同步字 | 补丁版同步字函数 | ID=99 → `SYNC=KEY`；ID=0/1/37/98 → 原厂 `50024/(ID+1)`；SCAL/SIDLE 收尾序列保留 | 桩替换 `write_reg`/`strobe`/`delay`，记录调用序列 |
| Unicorn-双发顺序 | 补丁版 TX4 / TX2 | ID=99：`SYNC=KEY → FIFO → SYNC=0x01F4 → FIFO → SYNC=KEY`；ID=0/5：只发一帧（原厂序列） | 直接执行补丁后的发送入口机器码 |
| Unicorn-原厂自证 | 原厂镜像（同一 harness） | ID=0/1/37/99 → 原厂公式；TX4/TX2 单发序列与原厂一致 | 证明「补丁只改了该改的」 |

### 1.2 关键期望值（可手工核对）

| 项 | 期望 |
|---|---|
| 密钥 KEY（示例） | `0xD798`（16 位；同一套系统里所有灯/引闪器必须一致） |
| KEY 写入同步字 | `SYNC1 = KEY>>8`、`SYNC0 = KEY&0xFF`（`0xD7 / 0x98`） |
| 第二帧同步字 | `floor(50024/(99+1)) = floor(500.24) = 500 = 0x01F4` |
| 原厂公式抽查 | ID=0 → `0xC368`；ID=1 → `0x61B4`；ID=37 → `0x0524`；ID=99 → `0x01F4` |
| 4 字节帧序列（TX4） | `FIFO(4) → strobe(0x35) → delay(600µs) → strobe(0x3B) → strobe(0x36)` |
| 2 字节帧序列（TX2） | `FIFO(2) → strobe(0x35) → strobe(0x3B) → strobe(0x36)`（原厂函数体在 FIFO 前还有 `delay(40µs)`；harness 只记录 FIFO/strobe，不记录延时） |

> 上面的原厂公式抽查值来自 `50024/(ID+1)` 的整数除法；若离线输出与它们不符，先怀疑固件版本/基址，
> 再怀疑 harness。

### 1.3 怎么记录结果

```powershell
# 仓库根；把整个输出留档（不要只记"通过了"）
tools\python\python.exe keypatch\keypatch.py patch --device x3pros --key 0xD798 --verify --out %TEMP%\kp_x3pros | Tee-Object %TEMP%\x3pros_verify.log
```

- 全部 `[PASS]` 才继续；
- 任一 `[FAIL]` ≈ 固件版本/补丁模块地址常量不符，**不要**刷机；
- 输出文件长度必须仍是 **1,931,868 B**，且差异只出现在补丁点（§1.1 第 3 行）。

## 2. 复现命令

```powershell
# 0) 设备/固件是否就位（应输出 sha256 OK）
tools\python\python.exe keypatch\keypatch.py list
tools\python\python.exe keypatch\keypatch.py info --device x3pros

# 1) 打补丁 + 离线验证
tools\python\python.exe keypatch\keypatch.py patch --device x3pros --key 0xD798 --verify --out %TEMP%\kp_x3pros

# 2) 生成 G3 容器备用件（裸 bin 报"不匹配"时再换）
tools\python\python.exe keypatch\keypatch.py patch --device x3pros --key 0xD798 --verify --container --out %TEMP%\kp_x3pros

# 3) 模块级直接跑 verify（便于看每项明细；需 x3pros 已注册到 DEVICE_IDS）
tools\python\python.exe -c "import sys; sys.path.insert(0,'keypatch'); from devices import x3pros; import common; raw=common.read_file('devices/x3pros/firmware/X3pro_S_v1.11_app.bin'); patched,log=x3pros.apply(raw,0xD798); [print(('PASS' if ok else 'FAIL'),msg) for ok,msg in x3pros.verify(patched,0xD798)]"

# 4) 全设备总自检（可选）
tools\python\python.exe keypatch\selftest.py --key 0xD798
```

产物命名：

- 裸固件：`X3pro_S_v1.11_app_keyD798.bin`（长度不变）；
- 容器备用件：`X3pro_S_v1.11_app_keyD798_container.bin`。

## 3. 离线验证覆盖不到的部分

1. **整机启动/主循环**：X3 Pro S 没有整机模拟器；启动链、外设、看门狗、显示/按键都没有回归；
2. **空口同步过滤**：Unicorn 只验证「写了正确的 SYNC1/SYNC0」，真正的射频同步过滤必须真机；
3. **双发时序**：第二帧整帧额外发射（TX2 帧内含约 500µs、TX4 帧内含约 600µs 延时）对
   HSS/连拍/高速同步/灯端响应的影响无法离线判断；
4. **2 字节短命令双发**：设置/属性类短命令被双发后，灯端是否出现额外提示音/状态重复等待实机观察；
5. **ID=99 语义代价**：密钥模式下 `ID=99` 不再表示普通 ID，用户侧确认；
6. **ID/设置的 flash 持久化**：本轮未逆向保存链，重启后 ID 是否保持需实测；
7. **G3 是否接受产物**：需真机/官方 G3 验证；容器格式只是兜底；
8. **热靴（Sony）功能**：热靴子镜像未改，但主固件发送路径被注入包装，TTL/HSS/热靴通信需实测。

## 4. 实机安全阶梯（风险自负，按顺序做）

> 前置：官方 G3 能识别设备；手上有 `devices/x3pros/firmware/X3pro_S_v1.11_app.bin` 可回滚；
> 已打过同一把 KEY 的灯（灯端密钥开关已打开，按各灯文档操作）。
> 判定口径：**引闪器 ID=99 = 密钥模式（双发）；ID=0..98 = 原厂普通模式（单发）。**

1. **原厂基线**：先用原厂 v1.11 确认设备能开机、菜单/按键正常、普通模式能引闪；
   同时确认能从官方渠道重新拿到同版本原厂固件（回滚用）。
2. **刷补丁版**：刷入 `X3pro_S_v1.11_app_keyD798.bin`，确认能正常开机、菜单/按键正常、
   版本信息仍为 **v1.11**（若 UI 显示），并至少能正常进入主界面不重启。
3. **普通模式（ID=0..98）**：设 ID 为 1..98，与同频道、同 ID 的原厂灯配合，确认能正常引闪；
   行为应与未打补丁的引闪器一致（单发）。
4. **密钥模式（ID=99）**：ID 调到 99，用已打同一把 KEY 的灯（同频道）确认能引闪；
   这一步同时验证「第一帧（KEY 同步字）生效」。
5. **兼容普通灯（第二帧）**：把一盏**原厂未打补丁**的灯设为**同频道 + ID=99**，
   用同一台补丁引闪器（ID=99）引闪，确认它能被第二帧（`SYNC=0x01F4`）引闪；
   再把这盏普通灯改成 ID=98，确认**不**被引闪（证明第二帧确实按 ID=99 发出）。
6. **隔离验证**：用**未打补丁的原厂引闪器**（同频道、ID=99）去引闪已打 KEY 的灯，
   确认灯**不被引闪**——这就是密钥生效的标志；再把补丁引闪器切回 ID=1（普通模式），
   确认 KEY 灯同样不被引闪。
7. **双发时序观察**：在密钥模式下测试 HSS/高速同步、连拍、引闪延迟；
   与第 1 步原厂基线对比。若出现漏闪/首包丢失/连拍异常，优先怀疑双发（[`../README.md`](../README.md) §5.6）；
   可重生成 `DUAL_SEND=False` 版本（密钥模式只发 KEY 单帧）作为对照。
8. **短命令帧观察**：在密钥模式下切换设置/属性（功率、造型灯、变焦等），
   观察灯端是否出现异常提示音、状态跳变或响应变慢。
9. **持久化**：重启引闪器，确认 ID=99 仍保持（若属原厂持久化语义）；再改回 0..98 确认恢复普通模式。
10. **G3 兼容**：若裸 `.bin` 被 G3 报「固件与设备不匹配」，改用
    `X3pro_S_v1.11_app_keyD798_container.bin` 重试；两种格式都记下结果。
11. **回滚**：任意一步异常 → 立刻刷回 `devices/x3pros/firmware/X3pro_S_v1.11_app.bin`
    （救砖/回滚流程见 [`keypatch/README.md`](../../../keypatch/README.md)）。

> 每一步**只引入一个变量**：先确认能开机，再确认普通模式，再确认密钥模式，最后才测时序。

## 6. 异常排查提示

| 现象 | 优先怀疑 | 处理 |
|---|---|---|
| 密钥模式下偶发首包丢失 | 第二帧把时序拉长 / 同步字切换窗口 | 用 `DUAL_SEND=False` 版本对照；仍异常则刷回原厂 |
| 密钥模式完全不响应 | 灯端是否同一把 KEY 且开关已开 / 引闪器 ID 是否真为 99 | 先核对 ID 与灯端密钥开关 |
| 密钥模式下灯能闪但偶发异常提示音 | 2 字节短命令被双发 | 记录现象；必要时切 `DUAL_SEND=False` |
| HSS/连拍漏闪 | 双发额外整帧发射（TX2 约 500µs / TX4 约 600µs 延时） | 对比原厂基线；`DUAL_SEND=False` 对照 |
| 普通模式异常 | 补丁点不符/固件版本不对 | 核对 sha256 与 3 个入口原始字节，重新生成 |
| 刷入后反复重启 | 注入区/入口补丁破坏了启动或主循环 | 立即刷回原厂；换版本重扫注入区引用并复核入口补丁 |
| G3 提示「选择的固件与设备不匹配」 | 设备需要容器格式 | 改用 `*_container.bin`；仍不行查设备 ID 字符串 |
| 刷坏后 G3 找不到设备 | — | 先正常开机 → 按一下侧拨轮 → 插 USB（救砖见 keypatch/README） |

## 7. 结论（当前）

- **离线**：静态身份/补丁点/差异范围检查 + Unicorn 调用级（同步字分流、TX4/TX2 双发顺序、
  原厂自证）已设计并可由 `--verify` 复现；**具体 PASS 项数以实际输出为准**；
- **无整机模拟器、无实机验证**：空口同步过滤、双发时序、G3 接受度、ID 持久化、
  Sony 热靴功能都必须在真机上按 §4 安全阶梯确认；
- 在实机验证完成前，本补丁应视为**实验性**，首次刷入务必保留原厂固件与回滚路径。
