# X3-S（X3 S 引闪器）v1.25 —— 静态证据与复现

> 本文件记录 **Godox X3-S V1.25** 私有密钥补丁（默认 keybtn 版：机内开关 + 双发；v1 fixed 为历史）
> 所依赖的静态证据与复现步骤。
> 配套脚本：`keypatch/dev/x3s/analyze.py`、`unicorn_sync_test.py`（v1 fixed 语义）、
> `keybtn_build.py`、`keybtn_runtime.py`、`boot_regression.py`。
> 补丁模块：`keypatch/devices/x3s.py`。

## 1. 镜像

| 项目 | 值 |
|---|---|
| 文件 | `devices/x3s/firmware/X3_S_v1.25_app.bin` |
| 大小 | 1,012,268 字节 |
| SHA-256 | `3cd40ef3f91369d3147c538cf6745f9308d82e14ad94c9bad9c8f129e0753e4d` |
| 基址 | `0x08004800` |
| 向量表 | SP=`0x200477C0`、Reset=`0x08004AF9`、NMI=`0x08010A65`、HardFault=`0x0800C0FD` |

向量表首字与 X3-C **完全相同**（SP=0x200477C0、Reset=0x08004AF9），Reset 偏移 0x2F9 落在
向量表之后；据此确认 App 基址仍是 `0x08004800`（AT32F435 平台，与 X3-C 同族）。

## 2. 与 X3-C 的代码对应（同一套代码，分段平移）

X3-S 与 X3-C 是同一套源码的两个机型构建：关键函数**逐字节相同**，只是地址按区段平移。
通过在本镜像中搜索 X3-C 函数的 16~32 字节前缀确认：

| 函数 | X3-C | X3-S | 平移 |
|---|---|---|---|
| `set_sync(id)` | `0x08014864` | **`0x0801474C`** | -0x118 |
| `set_channel(ch)` | `0x08014814` | `0x080146FC` | -0x118 |
| `WriteReg(reg,val)` | `0x08023540` | `0x08023428` | -0x118 |
| `Strobe(cmd)` | `0x08023520` | `0x08023408` | -0x118 |
| `delay(n)` | `0x080232B6` | `0x0802319E` | -0x118 |
| CC2500 初始化表 | `0x080232BC` | `0x080231A4` | -0x118 |
| 按键扫描 | `0x0800CC30` | **`0x0800CBD0`** | -0x60 |
| 读键 `FUN_08022EB4` | `0x08022EB4` | `0x08022D9C` | -0x118 |
| `send_short(cmd)` | `0x080118B0` | **`0x0801184C`** | -0x64 |
| `send_property(g,k,v)` | `0x0801184C` | **`0x080117E8`** | -0x64 |
| 低层发送 2 字节 | `0x0801712C` | `0x08017014` | -0x118 |
| 低层发送 4 字节 | `0x0801708C` | `0x08016F74` | -0x118 |

`set_sync` 函数头 32 字节与 X3-C 对应函数**逐字节相同**；RAM 布局也相同
（ID=`0x20000055`、状态结构=`0x20000030`、界面状态=`0x200003E7`、组帧门控=`0x20000146`
等两边同址同值）。

## 3. 同步字函数 `0x0801474C`

原厂反汇编（`analyze.py` §2 可复现）：

```asm
0x0801474C  10 b5            push  {r4, lr}
0x0801474E  4c f2 68 31      movw  r1, #0xC368      ; 50024（原厂公式分子）
0x08014752  40 1c            adds  r0, r0, #1       ; 除数 = ID + 1
0x08014754  b1 fb f0 f4      udiv  r4, r1, r0       ; sync = 50024 / (ID+1)
0x08014758  21 0a            lsrs  r1, r4, #8       ; SYNC1
0x0801475A  04 20            movs  r0, #4
0x0801475C  0e f0 64 fe      bl    0x08023428       ; WriteReg(4, SYNC1)
0x08014760  e1 b2            uxtb  r1, r4           ; SYNC0
0x08014762  05 20            movs  r0, #5
0x08014764  0e f0 60 fe      bl    0x08023428       ; WriteReg(5, SYNC0)
0x08014768  ...               （delay/SCAL/延时序列，双发补丁不改此函数）
```

## 4. v1「固定 KEY」补丁（历史，`apply_fixed`）

| 地址 | 原厂 | 补丁后 | 说明 |
|---|---|---|---|
| `0x0801474E` | `4c f2 68 31`（movw r1,#0xC368） | `movw r1,#KEY` | 被除数 50024 → 私有 KEY |
| `0x08014752` | `40 1c`（adds r0,r0,#1） | `01 20`（movs r0,#1） | 除数 ID+1 → 1 |

补丁后 `sync = KEY / 1 = KEY`（任意 ID）。差异 5 字节 / 长度不变。
独立 Unicorn 验证见 `unicorn_sync_test.py`：原厂镜像 4 个 ID 均为 `50024/(ID+1)`，
补丁镜像 4 个 ID 均为 KEY，写寄存器序列与收尾时序一致（ALL PASS）。

> v1 没有开关、不双发，只作为保守方案；默认成品是下节的 keybtn 版。

## 5. keybtn（默认）：双发 + 机内开关

### 5.1 核心双发（`0x080EE000`，344 B）

入口替换：

| 地址 | 原厂 | 补丁后 |
|---|---|---|
| `0x0801184C` | `10 b5 0a 4c`（push {r4,lr}; ldr r4,[pc,#0x28]） | `B.W 0x080EE000` |
| `0x080117E8` | `70 b5 0b 4c`（push {r4,r5,r6,lr}; ldr r4,[pc,#0x2c]） | `B.W 0x080EE0A0` |

注入逻辑（反汇编由 `analyze.py` §8 输出）：

```
inj_short(cmd):
    if KEY_ON != 0 or (ID == 99 and ID_OFF == 0):
        if cmd in {0x09,0x1A,0x21,0x29}: double_send(cmd)
        else: single_send(cmd)          # 休眠/心跳等保持原厂
    else: single_send(cmd)

double_send(cmd):
    WriteReg(4, KEY>>8); WriteReg(5, KEY&0xFF)
    tramp_short(cmd)                    # 原厂 send_short 函数体（KEY 帧）
    WriteReg(4, (50024/(ID+1))>>8); WriteReg(5, ...&0xFF)
    tramp_short(cmd)                    # 原厂 send_short 函数体（普通帧）

tramp_short: push {r4,lr}; r4=0x40020414; B.W 0x08011850   # 重建原序言后回函数体
tramp_prop : push {r4,r5,r6,lr}; r4=0x40020414; B.W 0x080117EC
```

* `send_property` 包装对**所有**属性帧双发（与 X3-C 一致）；
* 第二帧同步字用 M4 硬件 `UDIV` 现算，不调用原厂 `set_sync`（避免其 SCAL/1ms 延时）；
* 双发后同步字停留在普通值（= 原厂同 ID 状态），后续单发/收包不受影响。

### 5.2 机内开关（`0x080EE400`，186 B）

| 补丁点 | 原厂 | 补丁后 | 说明 |
|---|---|---|---|
| `0x0800CBD0` | `2d e9 f0 5f`（push.w {r4..ip,lr}） | `B.W 0x080EE400` | 按键扫描入口跳转 |

注入代码：先执行原序言 → `btn_update()`（每主循环一次）→ `B.W 0x0800CBD4` 回原函数体。

`btn_update`：

```
1. 读 GPIOA MODER，PA9 位(bit18..19)==00（输入模式）才继续（防待机重配引脚误判）
2. r0 = FUN_08022D9C(GPIOA, 0x0200)   # PA9 = 拨轮/M/C，0=按下
3. 去抖：连续 3 次按下才开始计数（u16 计数 @0x20001096，streak @0x20001098）
4. 计数到 30 → toggle: KEY_ON(0x20001080) ^= 1（每段长按只触发一次）
5. 计数 > 600 → 清零（异常一直按下时防卡死）
6. 松开 → 计数/去抖清零（不改 KEY_ON）
```

**不修改**原厂其它键的长按阈值（`0x0800CCB4` 的 `cmp #0x28`、`0x0800CD16` 的
`cmp #0x1E` 保持原样），所以 PA8/PB15 的原厂长按行为（关于页等）不受影响；PA9 本身
原厂无长按动作，本补丁只是「加」了一档长按。

## 6. 全镜像 SYNC 写入点扫描

`analyze.py` §5 对全镜像 11,603 条 BL/BLX 做了目标匹配，`WriteReg` 调用点共 77 处；
其中只有 **两类** 会写 CC2500 寄存器 4/5（SYNC1/SYNC0）：

1. `set_sync` 内的 `0x0801475C` / `0x08014764`；
2. CC2500 初始化表 `0x080231A4` 里的 `0x080231D2`（`SYNC1=0xC3`）与 `0x080231DA`（`SYNC0=0x68`）。

初始化表写在启动阶段（尚未发射），启动链 `0x08006F76 → 0x080231A4` 之后
`0x08006FCA → 0x08011884 → 0x080118FC → set_sync` 会用当前 ID 覆盖它。

## 7. 安全 RAM（KEY_ON = 0x20001080）

* X3-S 全镜像**没有任何字面量**指向 `0x20001080`（以及手势计数 `0x20001096..0x20001099`）；
* 用 X3-C 的 Unicorn 整机模型加载 **X3-S 原厂镜像**，对 `0x20001080..0x2000109F` 做写追踪：
  启动阶段只有 BSS 清零写（PC=`0x08004A88`）32 次（16 字节 ×2 次），30 万条指令内
  **没有任何其它写** → 是安全 RAM 字节；
* X3-S 与 X3-C 的 RAM 布局相同（同址同值的 RAM 字面量），X3-C 侧已由 40M 指令模拟器证实。

## 8. 注入区（空闲闪存）

* 文件从 `0x080ECE04` 到 `0x080F7A2C` 约 **0xB1FC 字节全 0xFF**；
* 全镜像无字面量/分支目标指向 `0x080EE000..0x080EEC00`；
* core 用 `0x080EE000..0x080EE158`（344 B），按键用 `0x080EE400..0x080EE4BA`（186 B），
  两者互不重叠，预留区分别 1 KiB / 2 KiB。

## 9. 验证结果（ALL PASS）

### 9.3 启动回归（`boot_regression.py`）

原厂 vs 补丁各跑 **1,200,000** 条指令：停止原因、指令数、最终 PC/SP/LR、
最近 **8192** 条 PC 轨迹逐条一致（PASS）——说明补丁不影响启动路径。

## 11. 风险

* **无实机验证**：刷写有风险，请保留原厂固件用于回滚。
* 键位映射沿用 X3-C 实机结论（PA9 = 拨轮/M/C）；X3-S 按键扫描代码与 X3-C 逐字节相同。
* KEY_ON 为 RAM 版，重启回普通模式。
* 双发白名单沿用 X3-C；若 X3-S 热靴触发命令不同，需补白名单（见 NOTES §风险）。
* 若官方 G3 工具报「固件与设备不匹配」，改用容器备用件
  `keypatch/out/X3S_v1.25_app_key<KEY>_container.bin`（内嵌文件名含 `X3S`）。
