# 新增设备接入指南（以 V1C / V862C 为目标）

本指南说明如何把一台**新的神牛（Godox）灯 / 引闪器**接入本仓库：
从原厂固件到 `keypatch` 补丁模块，最后在 **studio** 里自动出现卡片、可生成固件。

> 适用对象：V1C、V862C 等尚未支持的 2.4 GHz 设备。已支持设备见
> [`设备清单.md`](设备清单.md)。
>
> ⚠️ 全程只研究**你本人合法拥有**的设备；固件版权归厂商，不要分发。刷机有风险，
> 先确保官方 G3 能识别设备、且手上有同版本原厂固件可回滚。

---

## 0. 全景流程

```text
① 拿原厂固件 ──► ② 记 sha256 / 放 firmware/ ──► ③ 定镜像基址
      │
      ▼
④ 找「ID → CC2500 同步字」函数（定位 + 确认唯一性）
      │
      ▼
⑤ 写 keypatch/devices/<id>.py：DEVICE + apply() + verify()
      │
      ▼
⑥ 注册到 DEVICE_IDS ──► studio 自动出现卡片
      │
      ▼
⑦ 测试清单（静态 / Unicorn / 模拟器 / 实机安全阶梯）
```

预计工作量：固件/硬件资料齐全时，一台灯 0.5–2 天（含模拟器回归）；引闪器若需要
「双发」注入则更久（参考 X3-C 的 `DESIGN_TOGGLE.md`）。

## 1. 拿固件并登记

### 1.1 获取

- 从**官方渠道**（官网下载页 / 官方升级包）获取与设备版本一致的 `.bin`；
- 不要用网友魔改版、不要用从别人机器 dump 的镜像来当"原厂基准"（除非你明确知道其来源和版本）；
- 保留一份原始文件**只读**备份，用于回滚与 sha256 复核。

### 1.2 计算并记录 sha256

```powershell
# 仓库根
(Get-FileHash devices\v1c\firmware\V1C_V1.0.bin -Algorithm SHA256).Hash.ToLower()
```

或：

```powershell
tools\python\python.exe -c "import hashlib,sys;print(hashlib.sha256(open(sys.argv[1],'rb').read()).hexdigest())" devices\v1c\firmware\V1C_V1.0.bin
```

把结果写进：

- `devices/<id>/firmware/README.md`（该文件的模板见 `devices/_template/firmware/README.md`）；
- `keypatch/devices/<id>.py` 的 `DEVICE["sha256"]`（**必填**，防拿错版本）；
- [`设备清单.md`](设备清单.md) 表格。

### 1.3 放对位置

```text
devices/v1c/firmware/V1C_V1.0.bin
```

`*.bin` 已被 `.gitignore` 忽略，不会入库；studio「上传原厂固件」也保存到这里。

## 2. 判断镜像基址（base）

固件里的地址是**虚拟地址**，文件偏移 = 虚拟地址 − base。判断 base 的常用方法（按可靠性排序）：

1. **向量表初值**：镜像开头 4 字节 = 初始 MSP（应为 `0x2000xxxx`，RAM 内）；
   第 2 个字 = Reset_Handler（Thumb，最低位为 1）。Reset_Handler 落在哪个
   `0x0800xxxx` 区间，就能缩小 base 范围；再结合第 3 条确认。
2. **已知芯片族的 Flash 布局**：例如 STM32F0/AT32 的 bootloader 常占前 12–18 KB。
   已见：灯的 app base = `0x08003000`（前 12 KB 是 bootloader），X3-C 的 app base = `0x08004800`（前 18 KB）。
3. **代码自引用校验**：扫描 `ldr rX, [pc, #imm]` 的字面量池，看其中的指针是否都落在
   `[base, base+len)`；用 `tools/python`（capstone）反汇编一小段做交叉验证。
4. **模拟器试跑**：把镜像加载到候选 base，跑几万条指令，若立即 HardFault/跑飞，
   说明 base 或向量表不对；能跑到 main 任务循环即基本正确。
5. **对照官方升级包**：官方包若是容器格式，解开后 payload 的 base 可能与裸 bin 相同；若不同，
   以能跑通的为准。

把结论写进 `DEVICE["base"]`、`devices/<id>/docs/` 与 [`设备清单.md`](设备清单.md)。

## 3. 找到「ID → CC2500 同步字」函数

这是整个接入的**核心**。本工具的原理是把：

```c
sync = 50024 / (id + 1);
CC2500_WriteReg(4, sync >> 8);    // SYNC1
CC2500_WriteReg(5, sync & 0xFF);  // SYNC0
```

改写成「`sync = 你的私有 KEY`」。所以必须定位到这段代码，且确认**全镜像没有别的地方
在运行期写同步字**（否则补丁会被覆盖）。

### 3.1 从常量 50024 入手（最快）

`50024 = 0xC368`，在 Thumb 里通常以 32 位字面量 `68 c3 00 00`（小端）出现在代码附近的
字面量池。用仓库自带的 capstone 扫描：

```powershell
# 仓库根；<base> / <file> 换成实际值
tools\python\python.exe -c "
import sys; sys.path.insert(0,'keypatch')
from capstone import *
data = open(r'devices/v1c/firmware/V1C_V1.0.bin','rb').read()
base = 0x08003000
needle = (50024).to_bytes(4,'little')
hits = [i for i in range(len(data)-4) if data[i:i+4]==needle]
print('50024 字面量出现位置(文件偏移/虚拟地址):', [(hex(h), hex(base+h)) for h in hits])
md = Cs(CS_ARCH_ARM, CS_MODE_THUMB | CS_MODE_MCLASS)
for h in hits:
    lo = max(0, h-0x60); hi = min(len(data), h+0x40)
    for ins in md.disasm(data[lo:hi], base+lo):
        if abs(ins.address - (base+h)) < 0x60:
            print('  0x%08X: %-8s %s' % (ins.address, ins.mnemonic, ins.op_str))
"
```

要点：

- 字面量被 **LDR (literal)** 引用，通常在该函数尾部（+0x2C/+0x34 等偏移）；
- 找到引用的函数入口后，反汇编该函数：应能看到 `adds r1, rX, #1`（分母 = ID+1）、
  除法调用（`__aeabi_uidiv` / 硬件 `udiv` 或移位减法）、以及两次写 `r0=4`/`r0=5` 的寄存器写调用；
- 记录：函数入口、函数结束（下一个函数起点）、被它调用的 WriteReg/除法/延时辅助函数地址。

### 3.2 从 CC2500 寄存器写入入手（交叉验证）

同步字寄存器是 CC2500 的 `0x04`(SYNC1) / `0x05`(SYNC0)。搜索所有「把立即数 4、5 传给
写寄存器辅助函数」的调用点：

- 正常应只有 **两处**：初始化表写入（初值常为 `0xC3/0x68`）和本同步字函数；
- 若还有第三处运行期写入（例如设置恢复、休眠唤醒），必须一并处理或在 `verify()` 里说明；
- 确认同步字函数的所有调用点（初始化 / 改 ID 菜单 / 设置变化）都走同一个入口，
  这样只改这一个函数就够了。

### 3.3 记录证据

把下列内容写进 `devices/<id>/docs/04_sync_fn.md` 与 `keypatch/dev/<id>/NOTES.md`：

- 函数入口/结束地址、机器码长度、原始字节（`apply()` 里要逐字节校验）；
- 被调用的辅助函数地址（WriteReg / 除法 / 延时 / SCAL strobe）；
- 所有调用点及触发路径；
- 是否存在其它运行期同步字写入；
- 关掉 `SCAL(0x33)+1ms 延时` 的理由与风险（只改同步字、不改频率寄存器时通常不需要 SCAL，
  已支持的三台设备均如此处理）。

## 4. 写设备模块（`keypatch/devices/<id>.py`）

```powershell
# 仓库根
Copy-Item devices\_template\device.py keypatch\devices\<id>.py
```

按 [`devices/_template/device.py`](../devices/_template/device.py) 填写，重点是：

### 4.1 DEVICE 元数据

```python
DEVICE = {
    "id": "<id>",
    "name": "Godox <型号>",
    "kind": "flash",              # trigger | flash（studio 卡片）
    "model": "<型号>",
    "firmware_version": "<版本>",
    "image": "devices/<id>/firmware/<固件>.bin",
    "base": 0x08003000,
    "sha256": "<原厂 sha256>",
    "out_name": "<原厂固件名>_key{key:04X}.bin",
    "notes": "一句话说明",
}
```

### 4.2 `apply(data, key)` —— 原位补丁

硬性要求（`keypatch.py` 与 G3 都依赖它们）：

1. **输出长度 == 输入长度**，只改需要改的字节；
2. 改之前校验：`len(data) == IMAGE_SIZE`、`sha256`、每处补丁点的**原始字节**；
   不匹配立即 `raise ValueError`（防固件版本不对，也防把别人的机器刷坏）；
3. 补丁区不能越过目标函数的边界（例如下一个函数的起点），否则会破坏其它代码；
4. 返回 `(patched, patch_log)`，log 每项含 `addr` / `offset` / `before` / `after` / `desc`
   （`before`/`after` 为十六进制字符串），studio 会原样展示。

常见做法有两种（参考已支持设备）：

| 做法 | 适用 | 参考 |
|---|---|---|
| 整函数改写 | 函数足够短、有 56 字节左右空间放「读开关 + 选 KEY/原厂公式 + 写 SYNC1/0」 | `keypatch/devices/ad100.py`、`ad200.py` |
| 入口跳转 + 空闲区注入 | 需要在发送前后做更多事（如双发 KEY 帧 + 普通帧） | `keypatch/devices/x3c.py`、`DESIGN_TOGGLE.md` |

### 4.3 `verify(patched, key)` —— 离线验证

强烈建议实现（studio 的「离线验证」开关与 `keypatch.py --verify` 都用它）。推荐三层：

1. **静态**：长度不变；补丁区字节 == 期望；与原厂差异**只**落在补丁区；
2. **Unicorn 调用级**：加载补丁镜像，把 `WriteReg` / 除法 / 延时 / strobe 辅助函数入口改成
   `bx lr` 返回桩，用 code hook 记录参数；从同步字函数入口执行，断言
   `WriteReg(4, key>>8)`、`WriteReg(5, key&0xFF)`；多取几个 ID 验证；
3. **原厂自证**：同一 harness 跑原厂镜像，应得到 `50024/(ID+1)` 与原有 strobe/延时序列。

如果芯片不是 Cortex-M（或 Unicorn 不支持），可退化为静态检查，但要在 `verify()` 里明确说明。

### 4.4 依赖

- 模块**只能**依赖标准库 + `keypatch/common.py`；
- `capstone` / `unicorn` **只在 `verify()` 内部延迟导入**（导入阶段不能 import，否则 studio
  在无这些库的环境里无法列出设备）；
- 不写死绝对路径（`image` 用仓库相对路径）。

## 5. 注册设备 → studio 自动出现

1. 在 `keypatch/devices/__init__.py` 的 `DEVICE_IDS` 追加 `<id>`：

   ```python
   DEVICE_IDS = ["ad100", "ad200", "x3c", "<id>"]
   ```

2. （可选）在 `KEY.example.txt` / 文档里不需要额外改动——studio 会读 `list_devices()`：
   - `id` / `name` / `kind` / `model` / `firmware_version` → 设备卡片；
   - `image` + `firmware{present,path_abs,size,sha256_actual,matches}` → 固件就位状态；
     缺失或不匹配时，网页上会出现「上传原厂固件」按钮；
   - `out_name` → 生成文件命名；`notes` → 卡片备注；`features.verify/container` → 选项可用性。
3. 不需要改 `studio/server.py`；重启 studio 后 `GET /api/devices` 就会多一台设备。

自检注册是否成功（stdin 一条命令，等价于 studio 后端的调用）：

```powershell
tools\python\python.exe -c "import sys; sys.path.insert(0,'keypatch'); import devices, json; print(json.dumps(devices.list_devices(), ensure_ascii=False, indent=2))"
```

## 6. 测试清单（必须全部通过再交付）

### 6.1 引擎/模块级

```powershell
# 语法
tools\python\python.exe -m py_compile keypatch\devices\<id>.py

# 能列出 + 固件 sha256 对得上
tools\python\python.exe keypatch\keypatch.py list
tools\python\python.exe keypatch\keypatch.py info --device <id>

# 打补丁 + 离线验证（先输出到 %TEMP%，不要覆盖正式成品）
tools\python\python.exe keypatch\keypatch.py patch --device <id> --key 0xD798 --verify --out %TEMP%\kp_<id>

# 容器备用件（文件名必须含设备 ID 字符串，否则 G3 会报"固件与设备不匹配"）
tools\python\python.exe keypatch\keypatch.py patch --device <id> --key 0xD798 --container --out %TEMP%\kp_<id>

# 全设备总自检
tools\python\python.exe keypatch\selftest.py --key 0xD798
```

验收标准：

- `patch --verify` 全部 `[PASS]`；
- 输出 bin 与原厂**长度一致**；
- 差异字节只出现在预期补丁点；
- `selftest.py` 结论 `ALL PASS`。

### 6.2 模拟器回归（有模拟器时）

- 原厂镜像与补丁镜像分别启动到主循环，PC/SP/任务计数同量级、无 fault；
- 触发「改 ID / 按开关」路径时，同步字按预期变化（Unicorn 调用级已覆盖，模拟器再兜一层）。

### 6.3 网页工坊（studio）

```powershell
tools\python\python.exe studio\server.py --port 18780 --open
```

- 设备卡片出现，固件状态「已就位 sha256 OK」；
- 生成一把密钥 → 下载 `.bin`，再用 `keypatch.py verify` 复核；
- 勾选「G3 容器备用件」时能导出 `*_container.bin`。

### 6.4 实机（风险自负，安全阶梯）

1. **原厂**：先确认能从官网重下同版本原厂固件、官方 G3 能识别设备；
2. **纯静态/最小补丁**：只改同步字、不改 UI；刷入后确认能开机、菜单正常、普通模式能引闪；
3. **开关逻辑**：打开密钥开关 → 只有打过补丁的引闪器能引闪；关闭 → 恢复原厂行为；
4. **隔离验证**：把引闪器切回普通模式（原厂 ID），密钥模式的灯应**不被引闪**（这就是密钥生效）；
5. 任何一步异常，立刻刷回原厂（救砖方法见 `keypatch/README.md`）。

## 7. 风险与限制

1. **无实机验证的结论都不算数**：静态分析 + Unicorn/模拟器只能证明"代码按预期执行"，
   真正的空口同步过滤必须靠真机 CC2500 硬件验证。
2. **16 位同步字不是密码学认证**：挡的是正常原厂设备误触发，SDR 抓包理论上可克隆。
3. **版本绑定**：补丁点原始字节与 sha256 强校验；官方一旦升级固件版本，需要重新定位补丁点。
4. **删 SCAL/延时**：只改同步字、不改频率寄存器时通常不需要 SCAL；若实机出现首包丢失，
   优先怀疑这里（回退方案：保留原厂 strobe 序列并缩到 56 字节内，或改为注入方案）。
5. **开关持久化**：灯的 C.Fn 开关若复用某设置字节，必须确认该字节随 flash 参数区持久化；
   引闪器若用 RAM 字节，重启会复位（X3-C 当前就是 RAM 版）。
6. **G3 容器**：只有少数 V2.0/A1 设备需要容器格式；容器内嵌文件名**必须包含设备 ID**。
7. **不要动 bootloader**：补丁只碰 app 区；只要 bootloader 完好、G3 能识别，就能刷回原厂。
8. **文件长度**：原位补丁保持长度不变最稳；需要注入时，必须确认注入区在目标版本里
   是擦除态 `0xFF` 且无任何字面量/分支引用。

## 8. V1C / V862C 接入待确认清单

拿到设备/固件后，按顺序回答这些问题（答案写进 `devices/<id>/docs/`）：

- [ ] MCU 型号与内核（Cortex-M0/M4？Flash/RAM 多大？）→ 决定能否用 Unicorn 验证；
- [ ] 镜像基址（`0x08003000`？`0x08004800`？是否整片 flash？）；
- [ ] 固件的 ID 设置入口（菜单/APP/拨轮），ID 范围是否也是 0..99；
- [ ] 「ID → 同步字」函数地址、56 字节内是否有足够空间；
- [ ] 全镜像是否只有该函数写 SYNC1/SYNC0；初始化写的是否会被覆盖；
- [ ] 是否需要在发送前后改同步字（决定用整函数改写还是入口注入 + 双发）；
- [ ] 开关放哪里（C.Fn 菜单项 / 物理键 / APP），开关字节在 RAM 哪里、是否持久化；
- [ ] 显示/UI 是否要改（能不碰 UI 就不碰，风险最低）；
- [ ] 原厂固件获取渠道、sha256、可回滚版本；
- [ ] 是否需要 G3 容器（V2.0/A1 设备）；
- [ ] 模拟器是否能跑起来（决定回归测试能做到什么程度）。

全部有答案后，按本指南第 4–6 节实现并测试即可。

## 9. 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `keypatch.py list` 显示 `sha256 MISMATCH` 或固件缺失 | 文件放错目录 / 版本不符 | 放到 `devices/<id>/firmware/` 并核对 sha256 |
| `apply()` 抛「原始字节与预期不符」 | 固件版本与补丁点不匹配 | 重新定位补丁点；不要强行跳过校验 |
| G3 提示「选择的固件与设备不匹配」 | 设备是 V2.0/A1，需要容器 | 用 `--container` 生成 `*_container.bin`（内嵌文件名含设备 ID） |
| studio 里看不到新设备 | 忘了加 `DEVICE_IDS` / 模块导入报错 | 看 `devices.list_load_errors()`；重启 studio |
| studio 能列设备但生成失败 | `apply()` 抛异常（常见：固件路径/版本不对） | 先在命令行跑 `keypatch.py patch --verify` 定位 |
| 补丁后设备反复重启/关机 | 注入/UI 补丁破坏了 RAM 或控件结构 | 退回"只核心补丁"版本，逐项加回（X3-C 有 `_core.bin` 安全阶梯先例） |
| 刷坏后 G3 找不到设备 | — | 先正常开机 → 按一下侧拨轮 → 插 USB；仍不行换线/口；最后才考虑 SWD |
